# Генератор бэклога на GitHub

Заведи milestones и issues по плану: $ARGUMENTS

## Порядок работы

1. Прочитай план целиком. Задачи — это строки `- [ ]` в блоке «Задачи» каждой
   фазы; «Цель», «Затрагивает» и «Когда готова» в issues не превращаются, они
   уходят в описание milestone и в тело задач.
2. Проверь доступ до того, как что-то создавать: `gh auth status` и
   `gh repo view --json nameWithOwner`. Не авторизован или репозиторий не тот —
   остановись и скажи об этом, а не создавай вслепую.
3. Собери, что уже заведено:

   ```bash
   gh api repos/:owner/:repo/milestones --jq '.[].title'
   gh issue list --state all --limit 200 --json title --jq '.[].title'
   ```

   Скилл запускают повторно после правки плана, и существующее дублировать
   нельзя: одинаковые milestones GitHub заводит молча, вторым.

4. Покажи, что собираешься создать — фазы, число задач в каждой, что из этого
   уже есть, — и дождись подтверждения. Issues видны всей команде, и удалять их
   потом придётся руками.
5. Создай milestones, потом issues, в порядке фаз: так номера issue идут по
   порядку работы.
6. В конце выведи таблицу: фаза → milestone (создан или уже был) → сколько
   issues создано и сколько пропущено как существующие.

## Milestone на фазу

```bash
gh api repos/:owner/:repo/milestones \
  -f title="Фаза 1: {название фазы}" \
  -f description="{Цель фазы}

Когда готова: {критерий из плана}"
```

- `title` — заголовок фазы целиком, вместе с номером: по нему же ищется дубль и
  на него ссылается `--milestone` у issues.
- В `description` обязательно уезжает «Когда готова». В issues этот критерий не
  помещается ни в одну задачу, а без него непонятно, когда milestone закрывать.
- `due_on` не ставь: дат в плане нет, а выдуманный дедлайн хуже отсутствующего.

## Issue на задачу

```bash
gh issue create --title "..." --body "..." --milestone "Фаза 1: {название фазы}" --label "..."
```

**Title** — текст задачи без `- [ ]` и без обратных кавычек. Задача длиннее ~70
символов — в title идёт её первое предложение, целиком текст всё равно будет в
теле.

**Body**:

```markdown
{полный текст задачи из плана}

**Фаза**: {заголовок фазы}

**Затрагивает**: {строка «Затрагивает» фазы}

**План**: {путь к файлу плана}
```

**Метки** ставь только те, что уже есть в репозитории — сверься с
`gh label list`. Несуществующая метка роняет `gh issue create` целиком, и issue
не создаётся вовсе. Нужной метки нет — либо заведи её одной явной командой
(`gh label create`), либо не ставь метку совсем; подставлять наугад нельзя.

## Правила

- Заголовки и тела issues пиши на русском, как и план.
- Issue — это задача из плана, а не твоё представление о том, как её делать. Не
  дописывай шаги, файлы и решения, которых в плане нет.
- Ни одна задача плана не остаётся без issue.
- Повторный запуск на том же плане ничего не пересоздаёт: заводится только то,
  чего ещё нет.
- Существующие issues и milestones скилл не правит и не закрывает — он только
  заводит новые.
- Если план не читается как фазы с задачами (нет заголовков «### Фаза N» или
  блоков «Задачи»), остановись и скажи об этом: молча угаданная разбивка даст
  бэклог, который никто не просил.
