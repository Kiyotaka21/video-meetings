# Генератор плана реализации

Составь план реализации по PRD: $ARGUMENTS

## Порядок работы

1. Прочитай PRD целиком. Если критерии готовности неполные или допускают
   несколько прочтений — задай уточняющие вопросы через `AskUserQuestion` и
   дождись ответов. План составляй только когда картина полная.
2. Имя файла плана получается из имени PRD заменой префикса:
   `docs/prd-meeting-file-upload.md` → `docs/plan-meeting-file-upload.md`. Так
   план и PRD всегда лежат парой.
3. Сохрани план в `docs/`.

## Структура плана

```markdown
# План: {название фичи}

**PRD**: {путь к файлу PRD}

**Дата**: {сегодняшняя дата в формате YYYY-MM-DD}

## Фазы реализации

### Фаза 1: {название}

**Цель**: что даёт эта фаза

**Затрагивает**: backend / frontend / база данных

**Задачи**:

- [ ] Задача 1
- [ ] Задача 2

**Когда готова**: проверяемый критерий

### Фаза 2: {название}

...
```

## Правила разбивки на фазы

- Первая фаза — минимальный сквозной путь (tracer bullet): пользователь видит
  результат целиком, пусть и урезанный.
- После любой фазы продукт остаётся рабочим — незаконченных кусков между
  фазами не остаётся.
- Не больше пяти задач в фазе. Получается больше — фазу надо делить.
- Фазы после первой не смешивают backend и frontend без необходимости.
- В каждой фазе есть задача на тесты, покрывающие то, что эта фаза добавила.

## Правила

- План пиши на русском.
- План покрывает все критерии готовности из PRD: ни один не остаётся без фазы.
- Не добавляй функциональность, которой нет в PRD.
- «Когда готова» — проверяемый критерий, а не «фаза сделана»: не «загрузка
  работает», а «файл 1 ГБ загружается, api отвечает 201, файл лежит на диске».
