# PRD: Профиль пользователя

**Дата**: 2026-10-19

**Статус**: Draft

## Цель

У пользователя появляется страница профиля, где он задаёт имя, ставит аватар и
меняет пароль. Сейчас учётка — это голый e-mail: в кабинете вместо человека
виден адрес и иконка-заглушка, а сменить пароль нельзя вовсе, даже если он
утёк. Смена пароля при этом закрывает все остальные сессии — иначе после утечки
она ничего не защищает.

## Пользовательские сценарии

- Пользователь нажимает «Профиль» в карточке аккаунта на `/` -> попадает на
  `/profile` с тремя блоками: имя, аватар, пароль.
- Пользователь вводит имя и сохраняет -> видит подтверждение; на `/` карточка
  аккаунта показывает имя крупно, а адрес — под ним.
- Пользователь стирает имя и сохраняет -> имя сброшено, карточка на `/` снова
  показывает адрес, как до появления профиля.
- Пользователь выбирает изображение -> видит его в круге на странице профиля без
  перезагрузки; на `/` рядом с именем — тот же аватар.
- Пользователь выбирает файл не того формата или больше лимита -> получает отказ
  с причиной («Формат .heic не поддерживается», «Изображение больше 2 МБ») до
  отправки файла.
- Пользователь загружает новый аватар поверх старого -> старый пропадает везде,
  ссылка на него перестаёт открываться.
- Пользователь удаляет аватар и подтверждает -> вместо картинки снова иконка-
  заглушка.
- Пользователь вводит текущий пароль, новый и его повтор -> пароль сменён,
  пользователь остаётся в системе на этой вкладке.
- Пользователь ошибся в текущем пароле -> видит ошибку у поля «Текущий пароль»,
  остаётся на странице и в системе.
- Повтор не совпал с новым паролем -> ошибка у поля повтора, запрос не уходит.
- Пароль сменили, а на другом устройстве осталась открытая сессия -> там
  следующий запрос получает 401, пользователь видит «Сессия истекла» и
  попадает на `/login`.
- У пользователя истекла сессия, пока открыт профиль -> api отвечает 401,
  страница гасит сессию и уводит на `/login` — так же, как кабинет и страница
  встречи.

## В скоупе

**Имя**

- Одно необязательное поле «Имя». При регистрации не спрашивается.
- Пробелы по краям обрезаются; пустая строка или одни пробелы сбрасывают имя.
- До 50 символов, перевод строки и управляющие символы не принимаются.
- Пока имени нет, везде, где оно показывается, стоит адрес — как сейчас.

**Аватар**

- Загрузка, замена и удаление. Удаление — с подтверждением.
- Форматы: JPEG, PNG, WebP. Размер — до 2 МБ.
- Формат определяет содержимое файла, а не расширение и не заявленный тип:
  `.png`, внутри которого не PNG, отклоняется.
- Показывается кругом с обрезкой по центру; неквадратное изображение не
  растягивается.
- Виден на `/profile` и в карточке аккаунта на `/`. Без аватара — иконка-
  заглушка, как сейчас.
- У пользователя в каждый момент один аватар: замена и удаление убирают старый
  файл с диска.

**Смена пароля**

- Три поля: текущий пароль, новый, повтор нового.
- Новый пароль подчиняется тем же границам, что и при регистрации (8–128
  символов), и не совпадает с текущим.
- Неверный текущий пароль — отказ с понятным текстом, пароль не меняется.
- После смены все сессии, открытые до неё, недействительны на любом устройстве,
  кроме той вкладки, где пароль сменили: она продолжает работать без повторного
  входа.

**API**

- Изменение имени, загрузка аватара, удаление аватара, смена пароля — только
  для вошедшего пользователя и только над собственной учёткой.
- `/auth/me` отдаёт имя и ссылку на аватар вместе с `id` и `email`.
- Проверка формата, размера и границ полей на api обязательна и не полагается на
  проверку в браузере.
- Отказы по аватару и паролю — русским текстом, пригодным для показа как есть,
  по образцу 415/413/409 у файлов встречи.

**Интерфейс**

- Новая страница `/profile`, закрытая middleware `auth`.
- Ссылка «Профиль» в карточке аккаунта на `/`, ссылка обратно — на профиле.
- Три блока сохраняются независимо: ошибка в одном не сбрасывает ввод в двух
  других.
- Проверка формата и размера аватара, длины имени и границ пароля до отправки.
- Состояния страницы: загрузка, отказ api с «Повторить», 401 — выход на
  `/login`.

## Не в скоупе

- Смена e-mail.
- Восстановление пароля («Забыли пароль?»), письма и уведомления о смене пароля.
- Удаление учётки.
- Кадрирование, поворот и фильтры аватара в браузере; уменьшение и
  перекодирование изображения на сервере; анимированные аватары (GIF).
- Аватар в шапке сайта, на странице встречи и у участников встреч; просмотр
  профилей и аватаров других пользователей.
- Заглушка с инициалами вместо иконки.
- Список активных сессий, выход на конкретном устройстве, «выйти везде» без
  смены пароля.
- Ограничение частоты попыток — ни для смены пароля, ни для `/auth/login`.
- Имя в форме регистрации, раздельные имя и фамилия.
- Отзыв уже выданных ссылок на файлы встреч при смене пароля.

## Технические ограничения

- **Сведения о пользователе фронтенд берёт у `GET /auth/me`, а не из токена.**
  Это уже правило проекта: имя и ссылка на аватар добавляются в ответ `/auth/me`
  и в его тест, а не в payload JWT. Имя в токене к тому же жило бы до
  перевыпуска и не менялось бы после сохранения.
- **`/profile` требует решения в `routeRules`.** Это приватная страница, как `/`
  и `/meetings/**`: `ssr: false` плюс `X-Robots-Tag`. Без правила она унаследует
  SSR по умолчанию.
- **Шапка сайта не меняется.** Она намеренно статична: `/pricing`, `/login` и
  `/register` пререндерятся, и меню, собранное по куке, разошлось бы между
  статическим HTML и гидратацией.
- **Неверный текущий пароль не может отвечать 401.** На фронтенде 401 от api —
  это «сессия кончилась» (`isUnauthorized`): страница гасит куку и уводит на
  `/login`. Ошибка в поле формы выкинула бы пользователя из системы.
- **Отзыв сессий ломает нынешнюю stateless-проверку токена.** Guard
  `authenticated` сейчас проверяет только подпись и `exp`, в базу не ходит.
  Чтобы токен, выпущенный до смены пароля, получал 401, проверка должна знать
  состояние пользователя — это обращение к базе на каждом закрытом запросе.
- **Точность `iat` в JWT — секунда.** Если сравнивать время выпуска токена со
  временем смены пароля, токен, выпущенный в ту же секунду до смены, и новый
  токен, выданный сразу после неё, неразличимы. Схема отзыва должна это
  учитывать, а тест — проверять именно этот край.
- **Вкладка, сменившая пароль, не должна выкинуть сама себя.** Её текущий токен
  тоже выпущен до смены, поэтому ей нужен новый токен в ответ на смену, а кука
  `auth_token` перезаписывается с тем же `maxAge`, что и при входе.
- **Вкладки одного браузера делят одну куку.** Вторая вкладка, открытая до
  смены, держит старый токен в памяти, получает 401 и вызывает `logout()` —
  который стирает куку, где уже лежит новый токен, и выкидывает и первую вкладку.
  Обработка 401 должна отличать «моя сессия мертва» от «кука уже обновлена».
- **Файловые ссылки не отзываются.** Они подписаны отдельным секретом и живут
  15 минут (`FILE_LINK_EXPIRES_IN`); выданные до смены пароля доживают свой срок.
  Это осознанно: окно — минуты, а отзыв потребовал бы того же похода в базу на
  каждую отдачу файла.
- **Смена пароля — второй способ подбирать пароль.** Тот, кто увёл токен, может
  перебирать текущий пароль через эту операцию. Ограничения частоты нет нигде в
  проекте, включая `/auth/login`; argon2 замедляет перебор, но не останавливает.
  Это дыра, общая с логином, и закрывать её надо для обоих маршрутов сразу.
- **Восстановления пароля нет, поэтому повтор нового пароля обязателен.**
  Опечатка в новом пароле запирает учётку навсегда — исправить её некому.
- **`<img>` не шлёт заголовок `Authorization`** — та же проблема, что у плеера
  файлов. Но механизм файловых ссылок как есть не подходит: ссылка с 15-минутным
  токеном ломает аватар на открытой странице через 15 минут, а новый адрес при
  каждом запросе `/auth/me` убивает кэш браузера. Ссылка не должна позволять
  получить аватар другого пользователя перебором или по его `id`. Способ
  выбирается в ресерче.
- **Новый аватар обязан показываться сразу, хотя браузер кэширует картинки.**
  Один и тот же адрес для старого и нового изображения покажет старое до
  истечения кэша.
- **Аватар хранится на диске api, как файлы встреч, а не в базе.** Новых
  сервисов в `docker-compose.yml` нет; часть состояния и так лежит мимо compose,
  аватары добавляются туда же. Замена и удаление обязаны убирать старый файл,
  иначе каталог копит мусор, за который никто не отвечает.
- **Формат аватара проверяется по содержимому — в отличие от файлов встреч.**
  Там разбор сигнатуры осознанно не делался; здесь файл до 2 МБ, прочесть его
  начало дёшево, а изображение рисуется на наших страницах. SVG не принимается:
  открытый напрямую с origin'а api, он исполнит встроенный скрипт.
- **Изображение не уменьшается на сервере.** В круг 40px на `/` уезжает файл
  целиком; лимит 2 МБ — компромисс между качеством фото с телефона и весом
  страницы.
- **Лимиты продублированы на клиенте с теми же текстами.** Длина имени, форматы и
  размер аватара, границы пароля лежат и на api, и в утилитах `web`, как схема
  `credentials` и лимиты файлов: разъезд не поймают ни типы, ни сборка.
- **Тестам api по-прежнему хватает Postgres**, но тесты аватара пишут во
  временный `UPLOAD_DIR` и убирают за собой, как тесты загрузки файлов.

## Критерии готовности

**API**

- [ ] Имя `"  Анна Петрова  "` сохраняется как «Анна Петрова», `/auth/me` отдаёт
      его; пустая строка и строка из пробелов сбрасывают имя, `/auth/me`
      отдаёт `null`.
- [ ] Имя длиннее 50 символов или с переводом строки — 422, имя не меняется.
- [ ] JPEG, PNG и WebP до 2 МБ принимаются; `/auth/me` отдаёт ссылку, по
      которой приходит то же изображение байт в байт с `Content-Type` своего
      формата.
- [ ] Изображение больше 2 МБ — 413, на диске ничего не остаётся.
- [ ] GIF, SVG, HEIC и файл `.png` с не-изображением внутри — 415.
- [ ] После замены аватара на диске у пользователя ровно один файл аватара,
      прежняя ссылка отвечает 404.
- [ ] После удаления аватара `/auth/me` отдаёт `null` вместо ссылки, файла на
      диске нет, прежняя ссылка отвечает 404.
- [ ] Ссылку на аватар нельзя составить, зная только `id` пользователя: запрос
      по предсказуемому адресу аватара другого пользователя не отдаёт
      изображение.
- [ ] Смена пароля с верным текущим проходит и возвращает новый токен; после неё
      `/auth/login` со старым паролем — 401, с новым — 200.
- [ ] Неверный текущий пароль — отказ с кодом, отличным от 401, и русским
      текстом; вход со старым паролем после этого по-прежнему проходит.
- [ ] Новый пароль короче 8 или длиннее 128 символов — 422; совпадающий с
      текущим — отказ с русским текстом.
- [ ] Токен, выпущенный до смены пароля, — 401 на `/auth/me`, `/meetings` и
      `/meetings/:id/files`, в том числе токен, выпущенный в ту же секунду, что
      и смена; токен из ответа на смену проходит.
- [ ] Все операции профиля без токена или с негодным токеном — 401.
- [ ] e2e-тесты в `apps/api/tests` покрывают: имя (сохранение, обрезка, сброс,
      отказы), аватар (три формата, 413, 415 по содержимому, замена, удаление,
      чужой аватар), смену пароля (успех, неверный текущий, границы, совпадение
      с текущим) и отзыв старых токенов, включая край в одну секунду.

**Интерфейс**

- [ ] С `/` на `/profile` ведёт ссылка «Профиль» в карточке аккаунта; `/profile`
      без куки уводит на `/login` без запросов к api.
- [ ] После сохранения имени карточка на `/` показывает имя и адрес под ним без
      перезагрузки страницы; без имени — адрес, как сейчас. Имя `<b>Анна</b>`
      показывается текстом, а не разметкой.
- [ ] Выбор GIF, SVG, HEIC или изображения больше 2 МБ показывает причину отказа
      без сетевого запроса (в журнале запросов Playwright запроса нет).
- [ ] Загруженный аватар появляется на `/profile` без перезагрузки и на `/` при
      следующем заходе без жёсткого обновления кэша; после замены нигде не
      видно старого изображения.
- [ ] Изображение 1600×900 показывается кругом без искажения пропорций.
- [ ] У аватара есть текстовая альтернатива с именем (или адресом, если имени
      нет).
- [ ] Удаление аватара спрашивает подтверждение; первым фокус получает
      «Отмена»; после удаления на месте картинки — иконка-заглушка.
- [ ] Несовпадающий повтор пароля — ошибка у поля повтора без сетевого запроса;
      неверный текущий — ошибка у поля «Текущий пароль», пользователь остаётся
      на `/profile` и в системе.
- [ ] У полей пароля `autocomplete`: `current-password` у текущего,
      `new-password` у нового и повтора.
- [ ] После смены пароля вкладка остаётся в системе и после перезагрузки;
      второй браузерный контекст со старым токеном при следующем запросе видит
      «Сессия истекла» и попадает на `/login`.
- [ ] Вторая вкладка того же браузера, открытая до смены пароля, не выкидывает
      из системы ни себя, ни первую вкладку.
- [ ] Ответ 401 на `/profile` гасит сессию и уводит на `/login`.
- [ ] Отказ api выводится русским текстом в элементе с `role="alert"` или у
      своего поля; соседние элементы не сдвигаются (0px по
      `getBoundingClientRect()`).
- [ ] Страница проверена Playwright MCP: снапшот дерева доступности снят, обе
      темы, ширины 360px и десктоп, горизонтального скролла нет
      (`scrollWidth === clientWidth`), цели нажатия ≥ 24×24px, контраст текста
      ≥ 4.5:1, рамок и иконок ≥ 3:1, фокус после неудачной отправки — на первом
      поле с ошибкой.
