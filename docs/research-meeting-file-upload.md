## 2. Шесть решений, которые правят план

### 2.1. `await` у каждой записи в `FileSink` — это и есть «потоком, а не в память»

Главный критерий PRD («потребление памяти не растёт пропорционально размеру
файла») держится не на выборе `FileSink` вместо `formData()`, а на одном
`await` внутри цикла. Замер на 1 ГБ, `highWaterMark: 1 МиБ` в обоих случаях:

```
FileSink, await у каждой записи : RSS до 50 МБ, пик 56 МБ → +6 МБ,    1.0 с
FileSink, без await             : RSS до 56 МБ, пик 2479 МБ → +2423 МБ, 2.0 с
```

`write()` возвращает `number | Promise<number>`: число, если чанк уже ушёл на
диск, и промис, если запись отложена. Не дожидаясь промиса, цикл читает сокет
быстрее, чем диск успевает писать, и буфер `FileSink` растёт неограниченно —
для гигабайтного файла вдвое больше самого файла. Разница в один `await`, и
её не поймают ни типы (`await` от числа легален), ни линт, ни тесты на 5 МБ.

```ts
const writer = Bun.file(tmpPath).writer({ highWaterMark: 1024 * 1024 })

for await (const chunk of request.body as ReadableStream<Uint8Array>) {
  // Без await буфер FileSink растёт до размера файла: замер на 1 ГБ даёт
  // +2423 МБ RSS против +6 МБ с await. Тесты на мелких файлах разницы не видят.
  await writer.write(chunk)
}

await writer.end()
```

**Следствие для плана**: в фазе 1 к критерию «RSS вырастает не больше чем на
200 МБ» нужен не только замер вручную, но и комментарий у `await` в коде —
иначе следующая «оптимизация» его снимет.

### 2.2. `Range` в Elysia 1.4.30 приходится писать руками — авто-обработка Bun сломана

Bun.serve умеет отвечать `206` на `new Response(Bun.file(path))` сам. Через
Elysia это не работает: `createResponseHandler` (`adapter/utils.mjs:244`)
безусловно переупаковывает любой `Response`, возвращённый обработчиком:

```js
const newResponse = new Response(response.body, {
  headers: mergeHeaders(response.headers, set.headers),
  status: mergeStatus(response.status, set.status),
})
```

`response.body` — уже `ReadableStream`, а не `BunFile`, и связь с файлом, по
которой Bun включал авто-`Range`, теряется. Замер на 1.4.30: запрос с
`Range: bytes=0-99` к роуту, возвращающему `new Response(Bun.file(dest))`,
отвечает **200 и все 3 145 728 байт**. Регрессия заведена как
[elysia#1868](https://github.com/elysiajs/elysia/issues/1868), внесена в 1.4.23,
на момент ресерча открыта.

Тот же замер с ручной реализацией даёт ровно то, что нужно: 206,
`Content-Range: bytes 0-99/3145728`, 100 байт тела.

Два практических следствия:

- **`Content-Length` ставить явно.** У переупакованного ответа его нет, а
  `createResponseHandler` при отсутствии `content-length` и
  `transfer-encoding: chunked` уводит ответ в стриминговую ветку. Замер: у
  «авто» варианта `Content-Length` в ответе `null`. Без него `<video>` не знает
  длительности и на части браузеров не даёт перемотку.
- **План не ошибается, требуя ручной `Range`** — но причина не «так надёжнее», а
  «иначе молча вернётся 200». Это стоит записать в `apps/api/CLAUDE.md`:
  когда elysia#1868 починят, соблазн выкинуть ручной код появится снова.

### 2.3. Файловая ссылка — на производном секрете, а не на том же `JWT_SECRET`

План предлагает подписывать файловый токен тем же `JWT_SECRET` и различать
токены по claim'у `typ: 'file'`. Первая половина («сессионный токен не должен
открывать файл») решается проверкой в обработчике отдачи. Вторая («файловый не
должен открывать `/auth/me`») **не решается ничем из плана** — и сейчас дырявая.

Разбор текущего guard'а `authenticated` (`src/modules/auth.ts`) с файловым
токеном `{ sub: <id файла>, typ: 'file' }`, подписанным `JWT_SECRET`:

| Маршрут          | Что происходит                                                |
| ---------------- | ------------------------------------------------------------- |
| `GET /auth/me`   | 401 — пользователя с таким id нет, повезло                    |
| `GET /meetings`  | **200 и пустой массив** — `findMany({ ownerId: <id файла> })` |
| `POST /meetings` | 500 — нарушение внешнего ключа на `users`                     |

Guard проверяет только `typeof payload.sub === 'string'`, а `jwt.verify()` без
опций принимает любой токен с нашей подписью. Замер это подтверждает:
`verify(fileToken)` без `{ audience }` → `true`. Само по себе «200 с пустым
списком» не утечка, но граница аутентификации нарушена, и каждый новый закрытый
роут будет расширять последствия.

Два рабочих варианта, оба проверены:

**(а) Производный секрет — рекомендуется.** Второй инстанс плагина со своим
именем и ключом, выведенным из того же `JWT_SECRET`:

```ts
// src/modules/files/link.ts
const FILE_LINK_SECRET = createHmac('sha256', env.jwtSecret)
  .update('file-link-v1')
  .digest('base64url')

export const fileLinkJwt = jwt({
  name: 'fileJwt',
  secret: FILE_LINK_SECRET,
  exp: env.fileLinkExpiresIn, // 15m
})
```

Замер: оба декоратора (`jwt` и `fileJwt`) живут в одном приложении, перекрёстная
проверка возвращает `false` в обе стороны, `exp` per-call даёт ровно 900 секунд
против 604 800 у сессионного. Плюсы — новой переменной окружения не нужно,
`src/modules/auth.ts` не меняется, ранее выданные сессионные токены остаются
годными, а перепутать токены криптографически невозможно, а не «по проверке
claim'а, которую забудут добавить».

**(б) Claim `aud` на одном секрете.** `sign({ sub, aud: 'file' })` и
`verify(token, { audience: 'file' })` — `jose` проверяет `aud` сам. Работает
(замер), но требует переписать и guard `authenticated` на
`verify(token, { audience: 'session' })`, а это разом обнуляет все выданные
сессионные токены: пользователей выкинет на `/login` один раз.

`typ` из плана в любом случае стоит переименовать: в JOSE `typ` — параметр
**заголовка**, а не payload'а, и плагин уже пишет туда `"JWT"`. Одноимённый
claim в payload'е читается как ошибка.

**Сделано в фазе 3 по варианту (а)** — `src/modules/files/link.ts`, claim'а
`typ` нет вовсе: различает токены секрет. Тесты фиксируют обе стороны:
сессионный токен и токен, подписанный самим `JWT_SECRET`, на отдаче — 401;
файловый токен на `/auth/me`, `/meetings` и списке файлов — тоже 401.

### 2.4. `Content-Type` при отдаче — из нашей таблицы, а не из метаданных

PRD прямо пишет «`Content-Type` от клиента не доверенный», план фазы 3 —
«`Content-Type` из метаданных». Если метаданные хранят строку, пришедшую от
клиента, это одно и то же значение, и получается хранимая XSS: файл с
расширением `.pdf`, загруженный с заголовком `Content-Type: text/html`, отдаётся
как HTML с origin'а api (`localhost:3000`), то есть с того же origin'а, что и
`/docs` со Scalar.

Правило: заявленный тип **проверяется**, но наружу уходит канонический MIME из
таблицы форматов, привязанный к расширению. Плюс `X-Content-Type-Options: nosniff`
на роуте отдачи.

### 2.5. Расширение решает, MIME только подтверждает

План: «415 на расширение **или** заявленный тип вне обоих списков». Буквальная
реализация отобьёт годные файлы: браузер часто отдаёт пустую строку или
`application/octet-stream` для `.m4a`, `.webm`, `.mkv` — тип берётся из реестра
ОС, а на Windows он для этих расширений сплошь и рядом не зарегистрирован.

Рабочее правило:

1. расширение не в списке → 415 (расширение авторитетно);
2. заявленный тип пустой или `application/octet-stream` → пропускаем, пишем в
   метаданные канонический MIME расширения;
3. заявленный тип непустой и не входит в набор, разрешённый для этого
   расширения → 415.

Так `.zip` и `.exe` отбиваются по пункту 1, подмена типа — по пункту 3, а
честная загрузка `.m4a` из Chrome на Windows не ломается на пустом месте.

### 2.6. Транзакция не спасает от гонки на 21-м файле

План: «счёт и вставка — в одной транзакции, иначе два параллельных запроса
пролезут на 21-е место». В Postgres изоляция по умолчанию — `READ COMMITTED`, и
`SELECT count(*)` в транзакции **ничего не блокирует**: две параллельные
транзакции обе увидят 20 файлов, обе вставят 21-й, обе закоммитятся. Транзакция
здесь даёт атомарность, но не взаимное исключение.

Нужен замок на строке встречи — он же естественная единица сериализации:

```ts
await prisma.$transaction(async (tx) => {
  // Блокируем строку встречи: без этого два параллельных запроса оба
  // насчитают 20 и оба вставят 21-й — READ COMMITTED их не разведёт.
  await tx.$queryRaw`SELECT id FROM meetings WHERE id = ${meetingId}::uuid FOR UPDATE`

  const count = await tx.meetingFile.count({ where: { meetingId } })
  if (count >= MAX_FILES_PER_MEETING) throw new FileLimitReached()

  return tx.meetingFile.create({ data })
})
```

Альтернатива без raw SQL — `pg_advisory_xact_lock(hashtext($1))`; выбор между
ними вкусовой, отсутствие любого из них — баг.

Сделано в фазе 2, и по ходу всплыли три вещи:

- **`::uuid` в сниппете выше лишний и ломает запрос.** `@default(uuid(7))` без
  `@db.Uuid` даёт колонку `TEXT` (миграция `add_meetings`), и `text = uuid` в
  Postgres не сравнивается. В коде — `WHERE id = ${meetingId}` без приведения.
- **Замер 16: «N загрузок через `Promise.all`» гонку не воспроизводит.** Пять и
  десять параллельных загрузок на последнее место дали ровно один 201 и **без**
  `FOR UPDATE`, три прогона из трёх. Транзакции Prisma при этом идут параллельно
  (три `$transaction` стартуют за 12 мс), но через `app.handle` запросы доходят до
  вставки вразнобой, и окно между счётом и вставкой не перекрывается. Тест,
  который проходит при любом коде, ничего не проверяет.
- **Детерминированный вариант работает.** Тест сам держит транзакцию с
  `FOR UPDATE` и вставленным двадцатым файлом, опрашивает `pg_stat_activity`,
  пока загрузка не встанет в очередь за замком (`wait_event_type = 'Lock'`), и
  коммитит. Без замка в обработчике — 201 и 21 файл (загрузка насчитала 19 до
  коммита, а её `INSERT` всего лишь подождал `FOR KEY SHARE` внешнего ключа), три
  прогона из трёх; с замком — 409.

## 3. Фаза 1: приём файла

### 3.1. Транспорт: сырое тело плюс заголовки

Решение плана (сырое тело, `parse: 'none'`, имя и тип в заголовках) подтверждено
и типами, и запуском.

`parse: 'none'` есть в типах Elysia 1.4.30 (`ContentType` в `types.d.ts:371`), и
после него `context.request.body` остаётся нетронутым `ReadableStream`. Замер:
3 МБ, разбитые на чанки по 64 КБ, доехали до диска байт в байт.

Почему не `request.formData()` — в Bun он собирает файл в память целиком; почему
не своё разбиение multipart — готового потокового парсера под Bun нет, а писать
его ради одного поля бессмысленно.

### 3.2. Имя файла в заголовке обязано быть percent-encoded

Значение HTTP-заголовка — это байты Latin-1. Кириллическое имя не проходит
**ни на клиенте, ни на сервере**:

- в браузере `xhr.setRequestHeader('x-file-name', 'Отчёт.pdf')` бросает
  `TypeError` («String contains non ISO-8859-1 code point» в Chrome,
  «Value is not a valid ByteString»);
- замер в Bun: `new Headers({ 'x-file-name': 'Отчёт за квартал.pdf' })` →
  `Header 'x-file-name' has invalid value`. Тест, который соберёт такой
  `Request`, упадёт ещё до `app.handle`.

Контракт — `encodeURIComponent` на клиенте, `decodeURIComponent` на api, и оба
конца это знают:

```ts
// web
xhr.setRequestHeader('x-file-name', encodeURIComponent(file.name))
// api
const rawName = decodeURIComponent(headers['x-file-name'] ?? '')
```

`decodeURIComponent` бросает `URIError` на битой строке (`%zz`, одиночный `%`) —
это 400, а не 500. Замер round-trip для `Отчёт за квартал.pdf` — совпадение
побайтово.

Это та же ловушка, что уже записана в память проекта про `curl -d` в Git Bash,
но с другой стороны: там ломается кодировка тела, здесь — заголовка.

### 3.3. Порядок операций и атомарная публикация

`FileSink` не создаёт родительский каталог — замер даёт
`ENOENT: no such file or directory, open '...\missing\x.bin'`. Каталог встречи
нужно создавать явно (`mkdir(dir, { recursive: true })`).

Порядок, который переживает любой обрыв:

1. проверить владельца встречи (`findFirst({ id, ownerId })`) → 404;
2. разобрать имя и тип из заголовков → 400 на битые;
3. расширение и заявленный тип по таблице → 415;
4. `Content-Length` против лимита группы → 413;
5. предварительный счёт файлов встречи → 409 (дешёвая отсечка до записи 2 ГБ);
6. `id = Bun.randomUUIDv7()`, `mkdir`, пишем в `<meetingId>/<id><ext>.part`,
   считая байты;
7. по факту записанных байт снова лимит → 413, `.part` удаляем;
8. транзакция с `FOR UPDATE`: счёт и вставка строки → 409, `.part` удаляем;
9. `rename('<id><ext>.part', '<id><ext>')` → 201.

Смысл шага 9: пока файл пишется, он лежит под именем, которого нет в базе, и
роут отдачи на него не попадёт. Читатель никогда не видит недописанный файл, а
уборка после любого отказа — это удаление одного `.part`. Идентификатор
генерируется приложением (`Bun.randomUUIDv7()`, то же семейство, что
`@default(uuid(7))` в схеме), чтобы путь был известен до вставки.

`.part` без пары в базе — след от падения процесса; их подберёт та же
`removeMeetingFiles` при удалении встречи.

### 3.4. Отмена долетает до диска сама

Замер: клиент рвёт соединение посреди загрузки (`AbortController` + `fetch`,
по сокету ушло 2 359 296 байт) — цикл `for await` в обработчике бросает
`AbortError: The connection was closed.`. Отдельно слушать `request.signal` не
нужно, достаточно `try/catch` вокруг цикла:

```ts
try {
  for await (const chunk of request.body) {
    /* ... */
  }
} catch (error) {
  // Клиент нажал «Отменить» или потерял сеть. Недописанный .part — наш мусор.
  await writer.end()
  await Bun.file(partPath)
    .delete()
    .catch(() => {})
  throw error
}
```

В замере файл после уборки на диске отсутствует.

**Замер 20 (фаза 7): один раз обрыв пришёл без ошибки.** В прогоне Playwright
MCP загрузка 200 МиБ под эмуляцией сети DevTools (10 МБ/с) была отменена на
~31 %: в браузере запрос `net::ERR_ABORTED`, а api записал **85 295 104 байта
как готовый файл** — со строкой в базе и ответом 201, без единой ошибки в логе.
То есть цикл `for await` закончился штатно, не бросив `AbortError`.

Воспроизвести не удалось ни разу: сырой TCP с закрытием и со сбросом сокета, XHR
с `Blob` и с `File` с диска, под эмуляцией и без, с её снятием сразу после
отмены — везде `AbortError: The connection was closed.` и `Content-Length` в
заголовке. Механизм не найден, но факт есть, а защита дешёвая и верная при
любом механизме: тело короче собственного `Content-Length` по определению
неполное. Обработчик сверяет записанные байты с заголовком и на расхождении
удаляет `.part` и отвечает 400 (тест в `tests/files.e2e.test.ts`). Chunked-тело
без заголовка сверять не с чем — это остаётся риском.

### 3.5. `BigInt` роняет ответ — подтверждено

Замер на голом Elysia: роут, вернувший `{ size: 2n ** 31n }`, отвечает
**500 `JSON.stringify cannot serialize BigInt.`**; с `Number(size)` и схемой
`t.Number()` — 200 и `{"size":2147483648}`.

Тип поля в схеме всё равно `BigInt`: максимум `Int` в Postgres — 2 147 483 647
байт, то есть 2 ГБ минус один байт, и файл ровно на 2 ГиБ туда не влезает.
Конвертация — на границе ответа, рядом с `toISOString()` для дат:

```ts
const toResponse = (file: MeetingFileRow) => ({
  ...file,
  size: Number(file.size), // BigInt не сериализуется: 500 вместо ответа
  createdAt: file.createdAt.toISOString(),
})
```

`Number` безопасен: 2 ГБ — это 2.1e9, до `Number.MAX_SAFE_INTEGER` (9.0e15)
пять порядков.

### 3.6. `maxRequestBodySize` у Bun.serve — 128 МБ по умолчанию

Без правки `src/index.ts` загрузка обрывается на 128 МиБ: это дефолт
`Bun.serve` (`bun-types/serve.d.ts:753`, тот же дефолт продублирован в типах
Elysia — `universal/server.d.ts:33`). Замер: тело 6 МБ против лимита 4 МБ не
даёт читаемого 413 — клиент получает обрыв сокета
(`The socket connection was closed unexpectedly`), то есть в браузере это будет
«нет связи», а не «файл больше 2 ГБ».

Отсюда два вывода:

- лимит Bun ставится **заведомо выше** нашего, чтобы свой 413 с русским текстом
  успевал отработать первым. «Чуть выше» — например, 2 ГиБ + 64 МБ, как
  предлагалось здесь изначально, — не годится: замер 18 ниже, в итоге потолок
  64 ГиБ;
- `app.listen` принимает `Partial<Serve>`, так что править только `index.ts`:

```ts
app.listen({
  hostname: env.host,
  port: env.port,
  // Дефолт 128 МБ обрывает загрузку записи; держим запас над MAX_RECORDING_SIZE,
  // чтобы клиент получал наш 413 с текстом, а не молчаливый обрыв сокета.
  maxRequestBodySize: env.maxRequestBodySize,
})
```

**Замер 18 (фаза 2): «чуть выше» не работает.** С потолком 2 ГиБ + 64 МиБ
запись на 2.1 ГиБ из браузера (Chrome, Playwright MCP) получила
`net::ERR_CONNECTION_ABORTED`, а не наш 413. Сырой TCP-запрос с заголовками и
парой байт тела показывает, что происходит: при `Content-Length` сверх потолка
Bun отвечает сам — `HTTP/1.1 413 Request Entity Too Large` (у нашего обработчика
статус-строка `Payload Too Large`, так их и различать), но без CORS-заголовков и
закрывая соединение, пока браузер ещё шлёт тело. Браузер не видит ни кода, ни
текста — для него это пропавшая сеть.

| Потолок            | Заявлено 2.1 ГиБ | 3 ГиБ | 100 ГиБ |
| ------------------ | ---------------- | ----- | ------- |
| 2 ГиБ + 64 МиБ     | Bun              | Bun   | Bun     |
| 64 ГиБ             | наш              | наш   | Bun     |
| `MAX_SAFE_INTEGER` | наш              | наш   | наш     |

Вывод: потолок должен пропускать к обработчику всё, что может прислать живой
пользователь, — наш 413 по `Content-Length` срабатывает до чтения тела и
доезжает до браузера (документ 51 МиБ и запись 2.1 ГиБ после правки — 413 с
текстом за ~1 с, на диске ничего). Выбран 64 ГиБ: далеко за любой записью
встречи, но конечный. Защитой от раздутого JSON на остальных роутах потолок не
служит ни при 2 ГиБ, ни при 64 — Elysia читает такое тело в память целиком, и
лечится это лимитом на роут, а не потолком сервера.

Рядом стоит знать про `idleTimeout` (дефолт 10 с, максимум 255): он считает
**простой**, и пока байты идут, он сбрасывается, так что двухгигабайтная
загрузка по медленному каналу его не задевает. Задеть может зависший клиент,
который открыл запрос и молчит, — это ровно то поведение, которое нужно.

Отдельный риск: у Bun была история 32-битных переполнений в счётчике тела —
[#6504](https://github.com/oven-sh/bun/issues/6504) (лимит выше ~1e9 давал 413)
и [#21490](https://github.com/oven-sh/bun/issues/21490) (загрузка вставала на
1.58 ГБ). Оба закрыты, но именно на границе 2 ГБ. Критерий фазы 1 «запись 1 ГБ
проходит» этого класса ошибок **не поймает** — проверять нужно файлом чуть
больше 2 ГиБ на живом сервере, а не через `app.handle`.

## 4. Фаза 2: лимиты

### 4.1. `Content-Length` — основной рубеж, счётчик в потоке — страховка

Браузер всегда проставляет `Content-Length` для `Blob`/`File` в теле XHR, так
что заявленный размер есть всегда и стоит ноль. Это единственное место, где
отказ доезжает до клиента гарантированно: отвечая 413 в середине чтения тела,
сервер закрывает соединение, и часть клиентов увидит сетевую ошибку вместо
ответа.

Поэтому: `Content-Length` отсутствует или больше лимита → 413 **до** открытия
файла; счётчик в потоке ловит только клиента, который соврал, и там уже
неважно, прочитает ли он тело ответа.

### 4.2. Имя файла и путь

`../../etc/passwd` из имени в путь не попадает по построению: путь — это
`<UPLOAD_DIR>/<meetingId>/<fileId><ext>`, где `meetingId` уже проверен как uuid
из базы, `fileId` сгенерирован нами, а `ext` берётся из таблицы форматов по
совпадению, а не копируется из имени. Проверять `path.resolve(...).startsWith(UPLOAD_DIR)`
не требуется, но одна строка стоит дёшево и переживёт рефакторинг.

На что смотреть при разборе расширения:

- `path.extname('../../etc/passwd')` → `''` → 415 по пункту 1;
- `path.extname('.bashrc')` → `''` (ведущая точка расширением не считается);
- регистр — `.PDF` и `.pdf` одно и то же, сравнение по `toLowerCase()`;
- составные вроде `.tar.gz` `extname` не понимает, но их и нет в списках.

Исходное имя уходит в базу как есть, включая `../`, — этого требует критерий
PRD.

### 4.3. Таблица форматов в одном месте

```ts
// src/modules/files/limits.ts
export const RECORDING_MAX_SIZE = 2 * 1024 ** 3
export const DOCUMENT_MAX_SIZE = 50 * 1024 ** 2
export const MAX_FILES_PER_MEETING = 20

interface FormatSpec {
  kind: FileKind
  /** Что уходит в Content-Type при отдаче — не то, что прислал клиент. */
  mime: string
  /** Что принимаем в заголовке от клиента, помимо пустого и octet-stream. */
  accepts: readonly string[]
  maxSize: number
}

export const FORMATS: Record<string, FormatSpec> = {
  '.mp4': {
    kind: 'recording',
    mime: 'video/mp4',
    accepts: ['video/mp4'],
    maxSize: RECORDING_MAX_SIZE,
  },
  '.m4a': {
    kind: 'recording',
    mime: 'audio/mp4',
    accepts: ['audio/mp4', 'audio/x-m4a'],
    maxSize: RECORDING_MAX_SIZE,
  },
  // ...
}
```

Отсюда же строится `accept` для `<input type="file">` на клиенте — но только
как подсказка диалогу выбора: перетаскивание `accept` не соблюдает, и проверка
на клиенте всё равно своя (фаза 5).

## 5. Фаза 3: отдача

### 5.1. Разбор `Range`

Реализация, подтверждённая замером (206, `Content-Range: bytes 0-99/3145728`,
ровно 100 байт):

```ts
const size = file.size
const [start, end] = parseRange(request.headers.get('range'), size)

return new Response(file.slice(start, end + 1), {
  status: 206,
  headers: {
    'content-range': `bytes ${start}-${end}/${size}`,
    'content-length': String(end - start + 1),
    'accept-ranges': 'bytes',
  },
})
```

Чего не забыть в `parseRange`:

| Заголовок           | Ответ                                                |
| ------------------- | ---------------------------------------------------- |
| нет                 | 200, весь файл, `Content-Length: size`               |
| `bytes=0-99`        | 206, байты 0..99                                     |
| `bytes=100-`        | 206, от 100 до конца                                 |
| `bytes=-100`        | 206, **последние** 100 байт                          |
| `bytes=0-9,20-29`   | 200 и файл целиком — RFC 9110 разрешает игнорировать |
| `start >= size`     | 416 + `Content-Range: bytes */<size>`                |
| синтаксический брак | 200 и файл целиком, а не 400                         |

`Accept-Ranges: bytes` уходит во всех случаях — по нему плеер решает, показывать
ли перемотку.

**Замер 19 (фаза 3): сниппет выше в нашем приложении отдаёт лишнее.** Он
мерился на голом маршруте, а у нас в `set.headers` всегда есть CORS (и
`Accept-Ranges`). Как только там что-то есть, Elysia переупаковывает ответ через
`new Response(response.body, …)` — и поток `body` у `Response` из
`BunFile.slice()` **теряет конец куска**:

```
new Response(Bun.file(p).slice(0, 100))                  → 100 байт
new Response(new Response(Bun.file(p).slice(0, 100)).body) → 1000 байт
маршрут с set.headers, slice(0, 100)                       → 206 и 1000 байт (и через handle, и вживую)
тот же маршрут, slice(0, 100).stream()                     → 206 и 100 байт
```

Ловится только диапазоном, который кончается не на конце файла: `bytes=900-`
и `bytes=-100` проходили и с багом. Лечение — `.stream()` у куска, сделано в
`src/modules/files/content.ts`; тест на `bytes=0-99` сверяет тело побайтово.
Из таблицы выше в реализации добавились две строки: `bytes=50-10` (конец
раньше начала) и `bytes=-` — брак, то есть 200 и файл целиком.

### 5.2. Удалённый файл отдаётся как пустой, а не как ошибка

Замер: у `Bun.file()` на несуществующий путь `size === 0`, `exists()` — `false`,
а чтение `slice(0, 10)` **не бросает ничего** и даёт пустое тело.

Значит роут отдачи без явной проверки ответит 200 с нулём байт (или 416, потому
что `start >= 0 === size`) на файл, который удалили. План фазы 4 требует здесь
404 — и правильно требует. Проверка идёт по строке в базе; `file.exists()`
поверх неё — второй системный вызов на каждый чанк видео, и его лучше не
добавлять, а несогласованность «строка есть, файла нет» лечить на удалении.

**Пересмотрено в фазе 3: `exists()` стоит.** «На каждый чанк» — ошибка
рассуждения: чанки идут внутри одного ответа, а stat делается один раз на
запрос, в том числе на каждый `Range`-запрос плеера, — это дёшево. Зато без него
рассинхрон (`rename` упал после вставки строки, файл стёрли руками) отвечает
«успешным» пустым 200 вместо 404.

### 5.3. `Content-Disposition` можно ставить `attachment` всегда

`Content-Disposition: attachment` браузеры применяют только к навигациям
верхнего уровня и **игнорируют для подресурсов** — `<img>`, `<audio>`,
`<video>`. То есть один роут отдачи закрывает оба сценария PRD: запись играет в
`<video src=...>`, документ скачивается по клику на ссылку, и имя в обоих
случаях приходит из заголовка.

Кодировка имени — RFC 5987, обе формы сразу (замер: строка проходит валидацию
`Headers`, чего сырая кириллица не делает):

```ts
const ascii = name.replace(/[\u0000-\u001f\u007f-\uffff"\\]/g, '_')
set.headers['content-disposition'] =
  `attachment; filename="${ascii}"; filename*=UTF-8''${encodeURIComponent(name)}`
```

`filename=` в кавычках — для старых клиентов, `filename*=UTF-8''…` — то, что
прочитают все современные. Критерий PRD «документ скачивается под исходным
именем, включая кириллицу и пробелы» проверяется именно результатом скачивания:
атрибут `download` на кросс-origin ссылке (`5173` → `3000`) браузер
игнорирует.

### 5.4. CORS: заголовки загрузки пройдут, `Content-Disposition` наружу — нет

`@elysiajs/cors` 1.4.2 с дефолтами (`allowedHeaders: true`) отражает
`Access-Control-Request-Headers` обратно, поэтому preflight с `authorization`,
`x-file-name` и `content-type` пройдёт без правки `app.ts`.

Но `exposeHeaders: true` в этом плагине отражает имена **запросных** заголовков,
а не ответных: `Access-Control-Expose-Headers` окажется списком того, что
прислал клиент. Для нас это безразлично — `<video>` и `<a href>` не CORS-запросы
и заголовки читать не пытаются. Станет важно в день, когда фронтенд решит
достать имя файла из `Content-Disposition` через `fetch`: тогда придётся указать
`exposeHeaders: ['content-disposition', 'content-range']` списком.

## 6. Фаза 4: удаление

Замер на Windows снимает опасение про «файл занят»: `Bun.file(p).delete()`
проходит, пока другой читатель держит файл открытым, и этот читатель дочитывает
его до конца. Отдельной очереди отложенного удаления не нужно.

Порядок — сначала строка в базе, потом диск: осиротевший файл на диске безвреден
и будет убран вместе с каталогом встречи, а строка без файла даёт битую ссылку в
интерфейсе.

`removeMeetingFiles(meetingId)` — `rm(dir, { recursive: true, force: true })` из
`node:fs/promises`; `force: true` делает функцию идемпотентной, а заодно
подбирает `.part` от прерванных загрузок.

## 7. Фазы 5–6: фронтенд

### 7.1. `UFileUpload` вместо своей зоны перетаскивания

В Nuxt UI 4.11 есть готовый компонент: `variant="area"` даёт зону дропа,
`dropzone` и `interactive` включены по умолчанию, `v-model` отдаёт `File` при
`:multiple="false"`, есть слоты `label`, `description`, `actions`, `files`.

Под задачу: `:multiple="false"`, `:preview="false"` (список файлов рисуем свой —
он приходит от api, а не из инпута), `accept` из таблицы форматов.

Что компонент не решает и остаётся нашим:

- `accept` фильтрует диалог выбора, но **не перетаскивание** — проверка формата
  на клиенте обязательна;
- «дроп нескольких берёт первый и говорит об этом» — своя обработка, при
  `:multiple="false"` компонент отдаёт один `File`, но сообщить пользователю
  надо самим.

### 7.2. XHR и что именно показывает процент

`$fetch`/`ofetch` не сообщает о переданных байтах, а `fetch` с телом-потоком в
Chrome требует HTTP/2 и полноценно не работает на http — остаётся
`XMLHttpRequest`. Это решение плана, и оно единственное.

Неочевидность, которую стоит заложить в интерфейс: `xhr.upload.onprogress`
считает байты, **отданные в сокет**, а не записанные на диск api. Для 2 ГБ
процент дойдёт до 100 заметно раньше, чем придёт 201, и пользователь будет
смотреть на «100 %» неопределённое время. Полоса должна после 100 % переходить в
«Сохраняем…», иначе выглядит как зависание.

```ts
xhr.upload.onprogress = (event) => {
  if (event.lengthComputable) progress.value = Math.round((event.loaded / event.total) * 100)
}
// 100 % у onprogress — байты ушли в сокет, а не легли на диск: до 201 может
// пройти ещё время, и без смены подписи это читается как зависание.
xhr.upload.onload = () => (phase.value = 'saving')
```

`xhr.abort()` рвёт соединение, и обработчик api получает `AbortError` — цепочка
«кнопка Отменить → недописанный файл удалён» замкнута (замер 3.4).

### 7.3. Ссылка стареет, пока страница открыта

15 минут на `url` из списка — меньше, чем пользователь может держать страницу
открытой. План это учитывает («отказ плеера перезапрашивает список»), стоит
только назвать событие точно: у `<video>`/`<audio>` это `error` на элементе, и
`media.error.code` будет `MEDIA_ERR_SRC_NOT_SUPPORTED` (4) — 401 от api
неотличим от битого файла. Перезапрашивать список имеет смысл один раз, иначе
на действительно битом файле получится цикл.

Для документа та же проблема выглядит иначе: клик по протухшей ссылке откроет
вкладку с JSON `{"message":"Unauthorized"}`. Дешёвое лечение — перезапрашивать
список при возврате фокуса на вкладку (`visibilitychange`), тогда ссылки почти
всегда свежие.

## 8. Тесты

### 8.1. Временный `UPLOAD_DIR` живёт в `tests/setup.ts` целиком

Замер: `beforeAll`/`afterAll`, объявленные в preload-файле, срабатывают **один
раз на весь прогон** — `beforeAll` перед первым файлом, `afterAll` после
последнего. Значит каталог можно и создать, и убрать там же, не расставляя хуки
по тестовым файлам:

```ts
// tests/setup.ts
const uploadDir = mkdtempSync(join(tmpdir(), 'video-meetings-uploads-'))
Bun.env.UPLOAD_DIR = uploadDir // до первого импорта src/config/env.ts

afterAll(() => rmSync(uploadDir, { recursive: true, force: true }))
```

Порядок тот же, что уже описан в `apps/api/CLAUDE.md`: `env.ts` читает `Bun.env`
один раз на загрузке модуля, поэтому переменная ставится в preload, а не в тесте.

### 8.2. Чего `app.handle` не проверит

`app.handle` идёт мимо `Bun.serve`, поэтому **`maxRequestBodySize` в тестах не
действует**. Замер: тело 6 МБ при лимите 4 МБ через живой сервер обрывает сокет,
а через `app.handle` спокойно доезжает до обработчика и отвечает 200. Вывод:
настройка лимита Bun тестом не покрывается, её проверяют руками один раз —
файлом чуть больше 2 ГиБ на запущенном `bun run dev:api`.

Наши 413/415/409 через `app.handle` проверяются нормально.

### 8.3. Две мелочи, на которых тест упадёт не по делу

- **URL в `new Request` должен быть с точкой в хосте.** Замер: `http://x/ping`
  даёт 404 на любой маршрут, `http://localhost/ping` — 200. Существующий хелпер
  `tests/helpers/http.ts` уже собирает `http://localhost${path}`; свой хелпер для
  загрузки должен делать так же.
- **Кириллическое имя в заголовке теста не собрать напрямую.**
  `new Request(url, { headers: { 'x-file-name': 'Отчёт.pdf' } })` бросает
  исключение в самом Bun. В тесте, как и в браузере, имя идёт через
  `encodeURIComponent`.

### 8.4. Тело-поток в тестах

`new Request(url, { method: 'POST', body: <ReadableStream> })` в Bun работает и
**без** `duplex: 'half'` (замер — оба варианта дали одинаковый результат). Ставить
`duplex` не обязательно; если поставить, понадобится `@ts-expect-error` — в
типах `lib.dom` его нет.

Для 413 гоняем не гигабайты, а заявленный `Content-Length` — как и написано в
плане.

Замер 15 (фаза 2): через `app.handle` заголовок `Content-Length` у запроса есть,
только если тест поставил его сам — `new Request(url, { body: 'hello' })` его
не проставляет, обработчик видит `undefined`. Поставленный руками доезжает как
есть, даже если врёт о длине тела (`'2'` при 10 байтах, `'abc'`). Два следствия:

- отсутствие `Content-Length` api обязан пропускать к счётчику в потоке, а не
  отбивать — иначе упадёт каждый тест со строковым телом (и chunked-загрузка на
  живом сервере);
- тест изображает «клиента, который соврал», просто заявляя размер отдельно от
  тела — поле `declaredSize` у `postFile` в `tests/helpers/http.ts`.

## 9. Окружение и конфигурация

| Переменная              | Дефолт       | Кто читает                                 |
| ----------------------- | ------------ | ------------------------------------------ |
| `UPLOAD_DIR`            | `./.uploads` | `src/modules/files/storage.ts` через `env` |
| `FILE_LINK_EXPIRES_IN`  | `15m`        | плагин файловых токенов                    |
| `MAX_REQUEST_BODY_SIZE` | `64 ГиБ`     | `src/index.ts` → `app.listen`              |

Дефолт у `UPLOAD_DIR` осмысленно оставить (в отличие от `DATABASE_URL` и
`JWT_SECRET`): отсутствие каталога загрузок не создаёт дыры в безопасности, а
падение api при старте на свежем клоне создаёт лишнее трение. Каталог — в
`.gitignore` и в `.prettierignore` (иначе `bun run check` попробует
отформатировать загруженные `.md` и `.csv` — они входят в список форматов PRD).

`MAX_REQUEST_BODY_SIZE` отдельной переменной, а не константой, потому что это
единственный лимит, который придётся поднимать при смене лимита записи, и
единственный, чей отказ выглядит как сетевая ошибка, а не как ответ api.
