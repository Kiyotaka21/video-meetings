# План: Профиль пользователя

**PRD**: `docs/prd-user-profile.md`

**Дата**: 2026-10-19

## Развилки, закрытые до плана

PRD оставлял открытым способ отдачи аватара и не фиксировал, как именно
отзываются сессии; решения приняты и зашиты в фазы:

- **Аватар — открытая ссылка со случайным ключом.** `GET /avatars/<ключ>.<ext>`
  без токена; ключ — 128 бит случайности, новый при каждой загрузке, не uuid v7
  (тот выводится из времени) и не id пользователя. Адрес меняется при замене,
  поэтому отдача идёт с `Cache-Control: immutable`: браузер кэширует картинку
  навсегда, а новый аватар виден сразу. Плата: картинку видит любой, у кого есть
  ссылка, без входа.
- **Отзыв сессий — счётчик версии, а не сравнение `iat` со временем смены.** У
  пользователя заводится `tokenVersion`, токен несёт claim `ver`, guard сверяет
  их. Сравнение по времени упирается в точность `iat` (секунда): токен, выпущенный
  за мгновение до смены, и новый, выданный сразу после неё, неразличимы. У
  счётчика такого края нет. Токен без `ver` (выпущен до выкатки) считается
  версией 0 — выкатка никого не разлогинивает. Плата: guard читает строку
  пользователя по первичному ключу на каждом закрытом запросе.
- **Коды отказов смены пароля.** Неверный текущий пароль — 403, новый совпадает
  с текущим — 400, оба с русским текстом для показа как есть. Не 401: на
  фронтенде он означает конец сессии. Границы полей по-прежнему отбивает схема
  — 422.
- **Маршруты — под `/auth/me`.** `PATCH /auth/me` (имя),
  `POST /auth/me/password`, `PUT` и `DELETE /auth/me/avatar` — все в
  `currentUserRoutes`, под guard'ом. Ответ на правку имени и аватара — тот же
  объект, что у `GET /auth/me`, и фронтенд кладёт его в общий `user` без
  повторного запроса.
- **Аватар уезжает сырым телом, как файлы встречи.** `parse: 'none'` и
  `writeBody` из `files/storage.ts` с лимитом 2 МБ. Multipart Elysia разбирает в
  память до обработчика, а потолок тела у Bun — 64 ГиБ: chunked-тело без
  `Content-Length` легло бы в память целиком. Имя файла не хранится, поэтому
  заголовка `X-File-Name` нет. Прогресс для 2 МБ не нужен, и PRD его не требует —
  клиент шлёт `Blob` через `$fetch`.
- **Устаревшая вкладка отличается от мёртвой сессии по куке.** Перед `logout()`
  обработчик 401 перечитывает куку: если в ней уже не тот токен, с которым ушёл
  запрос, её обновила соседняя вкладка — берём новый токен и повторяем загрузку
  вместо выхода.

## Фазы реализации

### Фаза 1: Имя от формы профиля до карточки на `/`

**Цель**: сквозной путь целиком, пусть и урезанный — у пользователя есть
`/profile`, он сохраняет имя и видит его в кабинете. Без аватара и пароля.

**Затрагивает**: база данных, backend, frontend

**Задачи**:

- [x] Поле `name String?` у `User` и миграция в том же коммите. `GET /auth/me`
      отдаёт `name` (`null`, пока не задано); `PATCH /auth/me` в
      `currentUserRoutes`: пробелы по краям обрезаются, пустая строка — `null`,
      длина до 50 после обрезки, перевод строки и управляющие символы — 422.
      Ответ — тот же объект, что у `GET /auth/me`; в `response`-карте 401, у
      маршрута `detail.security`.
- [x] Тесты в `tests/auth.e2e.test.ts`: `"  Анна Петрова  "` сохраняется как
      «Анна Петрова» и приходит в `/auth/me`; `""` и `"   "` дают `null`; 51
      символ и `"Анна\nПетрова"` — 422, имя прежнее; без токена и с негодным — 401. Тест на форму ответа `/auth/me` дополняется полем `name`.
- [x] Страница `app/pages/profile.vue` с middleware `auth` и правило `routeRules`
      для `/profile` (`ssr: false` плюс `X-Robots-Tag`, `useSeoMeta` с
      `noindex`); в том же коммите — строка в таблице маршрутов
      `apps/web/CLAUDE.md` и в «Рендеринг во фронтенде» `README.md`. Загрузка
      через `fetchUser`, отказ — алерт с «Повторить», 401 — тост «Сессия
      истекла» и `logout()`, как в кабинете.
- [ ] Блок «Имя»: граница 50 и тексты в `app/utils/profile.ts` — копия api с
      предупреждением, как у `credentials`; `updateName` в `useAuth` пишет ответ
      в общий `user`, успех — тост. `AuthUser` в `app/types/auth.ts` получает
      `name`. `AccountCard` на `/`: имя крупно и адрес под ним, без имени —
      адрес, как сейчас; ссылка «Профиль», на профиле — ссылка назад к встречам.
- [ ] Прогон Playwright MCP: сохранение имени и переход на `/` без перезагрузки,
      сброс имени, `<b>Анна</b>` показан текстом, 51 символ — ошибка у поля без
      запроса к api, `/profile` без куки уводит на `/login`.

**Когда готова**: на `/profile` сохранено «Анна Петрова» — `PATCH /auth/me`
отвечает 200, на `/` карточка показывает «Анна Петрова» и адрес под ним без
перезагрузки; сохранённое пустое имя возвращает в карточку адрес; `/profile` без
куки уводит на `/login`, и в журнале запросов Playwright нет ни одного обращения
к api; `bun run test` зелёный.

### Фаза 2: Смена пароля и отзыв сессий на api

**Цель**: пароль можно сменить, зная текущий, и все токены, выпущенные до смены,
перестают открывать api — кроме нового, выданного в ответ.

**Затрагивает**: база данных, backend

**Задачи**:

- [ ] Поле `tokenVersion Int @default(0)` (`token_version`) и миграция. Токены
      `/auth/register` и `/auth/login` несут `ver`; guard `authenticated` и
      `/auth/me` читают строку пользователя по `sub` и сверяют `ver` (нет claim —
      0): расхождение или удалённый пользователь — 401.
- [ ] `POST /auth/me/password` с `{ currentPassword, newPassword }`: границы
      нового — 8–128, одна константа со схемой `credentials`. Текущий не
      совпал — 403 «Текущий пароль неверен»; новый равен текущему — 400 «Новый
      пароль совпадает с текущим»; иначе одним `update` — новый хеш и
      `tokenVersion: { increment: 1 }`, ответ `{ token }` с новым `ver`.
- [ ] Тесты `tests/password.e2e.test.ts`: успех — `/auth/login` со старым
      паролем 401, с новым 200; после 403 старый пароль по-прежнему входит;
      новый пароль на 7 и 129 символов — 422; совпадающий — 400; без токена — 401. Старый токен — 401 на `/auth/me`, `/meetings` и
      `/meetings/:id/files`, новый — 200. Край одной секунды: токен с тем же
      `iat`, что у нового, но прежним `ver` (выпущен `signJwt` из
      `tests/helpers/jwt.ts`) — 401.
- [ ] Документация: таблица маршрутов в `apps/api/CLAUDE.md` и раздел про
      guard — он теперь ходит в базу; почему счётчик, а не `iat`; почему токен
      без `ver` — версия 0; почему неверный текущий пароль — 403. В корневом
      `CLAUDE.md` — граница пароля теперь общая у трёх маршрутов.

**Когда готова**: `POST /auth/me/password` с верным текущим паролем отвечает 200
и токеном; токен, полученный входом до смены, на `GET /meetings` получает 401, а
новый — 200; неверный текущий пароль — 403, и вход со старым паролем после него
проходит; `bun run test` зелёный.

### Фаза 3: Смена пароля в интерфейсе

**Цель**: пользователь меняет пароль со страницы профиля и остаётся в системе;
чужие сессии выходят, а свои вкладки — нет.

**Затрагивает**: frontend

**Задачи**:

- [ ] Блок «Пароль» на `/profile`: три поля с `autocomplete`
      (`current-password`, `new-password`, `new-password`) и `help` под каждым —
      строка под полем существует заранее, и ошибка её не сдвигает. Проверка до
      отправки — границы из `app/utils/auth.ts`, несовпадение повтора — ошибка у
      поля повтора без запроса; фокус — в первое поле с ошибкой.
- [ ] `changePassword` в `useAuth`: токен из ответа пишется в куку `auth_token`
      с тем же `maxAge`, что при входе. 403 — ошибка у «Текущего пароля», 400 —
      у «Нового пароля», тексты api как есть; успех — тост, поля очищены,
      пользователь на месте.
- [ ] Обработка 401 одним хелпером в `useAuth` для `/`, `/meetings/[id]` и
      `/profile`: перед `logout()` перечитать куку; если там уже другой токен,
      чем ушёл с запросом, — взять его и повторить загрузку, а не выходить.
- [ ] Прогон Playwright MCP: неверный текущий пароль (403, ошибка у поля,
      пользователь на `/profile`); несовпадающий повтор (ни одного запроса);
      успешная смена и перезагрузка — в системе. Кука, подменённая на токен,
      сохранённый до смены, — «Сессия истекла» и `/login`. Две вкладки, пароль
      сменён во второй, первая без перезагрузки делает запрос (переход по ссылке
      или «Повторить») — обе остаются в системе.
- [ ] Раздел «Авторизация» в `apps/web/CLAUDE.md`: почему 401 перечитывает куку
      перед выходом и почему ошибка текущего пароля приходит 403.

**Когда готова**: смена пароля на `/profile` оставляет вкладку в системе и после
перезагрузки; со старым токеном в куке страница показывает «Сессия истекла» и
уводит на `/login`; вкладка, открытая до смены, после перехода по ссылке
остаётся в системе и не выкидывает вторую; несовпадающий повтор не даёт ни
одного запроса в журнале Playwright.

### Фаза 4: Аватар на api

**Цель**: api принимает, заменяет, удаляет и отдаёт аватар и сам отбивает всё,
что не является картинкой нужного формата и размера.

**Затрагивает**: база данных, backend

**Задачи**:

- [ ] Поле `avatarKey String? @unique` (`avatar_key`) и миграция. Файл лежит в
      `<UPLOAD_DIR>/avatars/<ключ><ext>`; `/auth/me` и все ответы о
      пользователе отдают `avatarUrl` — путь `/avatars/<ключ><ext>` от корня
      api — или `null`.
- [ ] `PUT /auth/me/avatar`: сырое тело и `writeBody` с лимитом 2 МБ — 413 по
      `Content-Length` до чтения и счётчиком в потоке. Формат — по сигнатуре
      первых байт (JPEG, PNG, WebP), расширение и заявленный тип не
      учитываются; остальное — 415 с русским текстом. Новый файл ложится под
      новым ключом; старый ключ читается и заменяется под замком строки
      пользователя (`FOR UPDATE`) в одной транзакции, старый файл удаляется
      после коммита.
- [ ] `DELETE /auth/me/avatar`: сначала строка, потом диск, как у файлов
      встречи; ответ — пользователь с `avatarUrl: null`. `GET /avatars/:file` —
      свой инстанс без guard'а: ключ ищется в базе (нет строки — 404, даже если
      файл на диске), `Content-Type` — по формату, `nosniff`,
      `Cache-Control: public, max-age=31536000, immutable`.
- [ ] Тесты `tests/avatar.e2e.test.ts`: JPEG, PNG и WebP — `avatarUrl` в
      `/auth/me`, байты и `Content-Type` по ссылке совпадают; 2 МБ + 1 байт —
      413 и по заголовку, и по факту, в `avatars/` ничего не осталось; GIF, SVG,
      HEIC и `.png` с текстом внутри — 415. Замена — файла старого ключа нет,
      его адрес — 404; удаление — `null`, файла нет, старый адрес 404.
      `/avatars/<id пользователя>` и `/avatars/<id>.png` — 404; `PUT` и
      `DELETE` без токена — 401.
- [ ] Документация: маршруты и раздел «Аватар» в `apps/api/CLAUDE.md` — почему
      открытая ссылка со случайным ключом, а не файловый токен; почему формат
      по содержимому, в отличие от файлов встречи; почему `immutable`. В
      «Базе данных» `README.md` — аватары лежат в `UPLOAD_DIR/avatars/` рядом с
      файлами встреч, мимо compose.

**Когда готова**: PNG на 1 МБ загружается с ответом 200, `/auth/me` отдаёт
`avatarUrl`, по нему без токена приходит тот же файл с `image/png` и
`immutable`; после замены файла старого ключа в `UPLOAD_DIR/avatars/` нет, а его
адрес отвечает 404; `.png` с текстом внутри — 415, 2 МБ + 1 байт — 413;
`bun run test` зелёный.

### Фаза 5: Аватар в интерфейсе

**Цель**: пользователь ставит, меняет и убирает аватар на профиле и видит его в
карточке на `/`.

**Затрагивает**: frontend

**Задачи**:

- [ ] Форматы (`.jpg`, `.jpeg`, `.png`, `.webp`), 2 МБ и тексты отказов в
      `app/utils/profile.ts` — копия api; проверка до отправки по расширению и
      размеру, на отказе ни одного запроса. Абзац «Лимиты загрузки тоже
      продублированы» в корневом `CLAUDE.md` дополняется аватаром.
- [ ] Блок «Аватар» на `/profile`: текущий аватар кругом с `object-cover`,
      «Загрузить» или «Заменить» — `$fetch` с телом-`Blob` на
      `PUT /auth/me/avatar`, ответ — в общий `user`; отказы 413 и 415 — текстом
      api. «Удалить» — подтверждение через `useOverlay`, первым фокус получает
      «Отмена».
- [ ] Аватар в `AccountCard` на `/` и на профиле: `avatarUrl` склеивается с
      `apiUrl` через `apiHref`; текстовая альтернатива — имя, без имени — адрес;
      без аватара — иконка-заглушка, как сейчас.
- [ ] Прогон Playwright MCP: JPEG 1600×900 показан кругом без искажения
      (`object-fit: cover`, круг квадратный); после замены на `/` без жёсткой
      перезагрузки другой `src`, старого в DOM нет; удаление возвращает
      заглушку; GIF, SVG, HEIC и файл на 3 МБ дают текст отказа и ни одного
      запроса к api.
- [ ] `apps/web/CLAUDE.md`: файлы профиля в таблице и неочевидности — почему без
      прогресса, почему тело — сырой `Blob`, почему клиент проверяет формат
      только по расширению.

**Когда готова**: загруженный JPEG 1600×900 виден на `/profile` кругом без
искажения сразу после ответа api, а на `/` — при переходе без жёсткой
перезагрузки; после замены нигде нет старого изображения; после удаления на
обеих страницах иконка-заглушка; выбор GIF показывает причину отказа, и в
журнале Playwright нет запроса к api.

      одном не сбрасывает ввод в двух других; появление ошибки не сдвигает

      4.5:1, рамок и иконок ≥ 3:1 (через `<canvas>`), фокус после неудачной
      отправки — на первом поле с ошибкой, сдвиг при ошибке — 0px.
- [ ] Правки по замерам и запись найденного в «Что проверено в браузере» и

      `README.md`; в `apps/api/.env.example` новых переменных нет — или они

- [ ] `bun run check` и `bun run test` при поднятом Postgres.

**Когда готова**: на 360px и десктопе в обеих темах горизонтального скролла нет,
все замеры чек-листа в норме; загрузка профиля показывает один `role="status"`,
отказ api — алерт с «Повторить», ошибка в блоке пароля не трогает введённое имя;
`bun run check` и `bun run test` зелёные; ни один файл документации не описывает

## Заметки для прогона

- Пользователя и данные для проверок заводить из браузера, а не seed-скриптом:
  скрипт заводит данные мимо путей, которыми ходит пользователь.
- Кириллическое имя не отправлять через `curl -d` в Git Bash: payload уезжает не
  в UTF-8, в базу попадают `U+FFFD`, и дефект выглядит как ошибка api. Имя
  вводить в браузере.
- Картинки для `browser_file_upload` класть в `.playwright-mcp/`: MCP-сервер
  принимает файлы только из своих корней, путь из системного temp отбивается.
  Скриншоты — туда же, с каталогом в имени.
- «Другое устройство» в одном браузере изображается подменой куки на токен,
  сохранённый до смены пароля, — у Playwright MCP один контекст, и вкладки
  делят куку.
- Тесты api ходят в настоящую базу: перед прогоном `bun run db:up` и
  `bun run db:migrate`, иначе падают на SQL; pre-commit-хук требует того же.
