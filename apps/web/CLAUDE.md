# CLAUDE.md — apps/web

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Общие правила монорепозитория — в корневом `CLAUDE.md`. Здесь только фронтенд.

## Стек

Nuxt 4.5 (Vue 3.5, Vite, Nitro). `srcDir` — папка `app/`, как принято в Nuxt 4:
страницы лежат в `app/pages/`, а не в корне воркспейса. Порт 5173.

```bash
bun run --filter @video-meetings/web dev        # или из корня: bun run dev:web
cd apps/web && bun run typecheck                # nuxt typecheck
cd apps/web && bun run build && bun run start   # Nitro-сервер из .output
```

Вёрстка — **Nuxt UI 4** (Reka UI + Tailwind CSS 4 + Tailwind Variants). Scoped CSS и
raw-палитра Tailwind не используются, см. раздел «Дизайн-система».

Тестов нет. Для Nuxt понадобился бы `@nuxt/test-utils` с Vitest.

## Задача с UI не закрывается без визуальной проверки

Любая правка, меняющая интерфейс — страница, компонент, класс, слот `:ui`, токен в
`app/app.config.ts` или `main.css` — **считается незавершённой, пока её не открыли в
живом браузере и не сверили со скиллом `ui-ux-pro-max`**. `bun run check` здесь
ничего не гарантирует: он проверяет типы и формат, а не контраст, фокус, сдвиг
вёрстки и горизонтальный скролл: все дефекты, которые находились этой проверкой,
спокойно проходили и typecheck, и линт.

Порядок:

1. Подключить скилл `ui-ux-pro-max` и вытащить правила по своей теме (для форм —
   категории Forms и Accessibility).
2. Поднять приложение: `bun run dev` (если правка ходит в api — вместе с ним).
3. Открыть изменённый экран MCP-сервером Playwright и снять **снапшот дерева
   доступности**, а не только скриншот: имена кнопок, `aria-invalid`,
   `aria-describedby` и роли видны только там.
4. Прогнать состояния, а не один «счастливый» вид: пустое, ошибка валидации,
   отказ api, загрузка, успех.
5. Проверить обе темы (переключатель в шапке) и две ширины — 360–390px и десктоп.
6. Записать в этот файл всё, что пришлось искать, с причиной.

Проверяется замером, а не на глаз:

| Что                                   | Норма                          | Чем мерить                                |
| ------------------------------------- | ------------------------------ | ----------------------------------------- |
| Контраст текста                       | 4.5:1 (крупный — 3:1)          | canvas 1×1 + `getImageData`, формула WCAG |
| Контраст рамок, иконок, состояний     | 3:1                            | то же, `borderColor`/`backgroundColor`    |
| Размер цели нажатия                   | 24×24 CSS px (WCAG 2.2 AA)     | `getBoundingClientRect()`                 |
| Горизонтальный скролл                 | `scrollWidth === clientWidth`  | сравнить на 360px                         |
| Сдвиг вёрстки при появлении сообщения | 0px                            | `top` соседнего элемента до и после       |
| Фокус после неудачной отправки        | первое поле с ошибкой          | `document.activeElement`                  |
| Объявление ошибки                     | `role="alert"` или `aria-live` | атрибуты в DOM, не глазами                |

Три ловушки, на которые уже наступали:

- **`search.py` из скилла в этом окружении не запускается — Python не установлен**
  (ни `python`, ни `py`). Данные лежат рядом:
  `.claude/skills/ui-ux-pro-max/data/ux-guidelines.csv` (119 правил) и
  `data/stacks/nuxt-ui.csv`. Читай их напрямую, а не пересказывай правила по памяти.
- **Контраст не считается регуляркой по `getComputedStyle`.** Tailwind 4 отдаёт
  цвета в `oklch`, фоны карточек — в `color-mix`, и наивный парсер молча выдаёт
  единицы вместо реальных значений. Резолвить должен браузер: залить цвет в
  `<canvas>` 1×1 и прочитать пиксель.
- **`focus()` на выключённом поле молча ничего не делает.** У `UForm` за это
  отвечает `loadingAuto`, у watcher'а — дефолтный `flush: 'pre'` (срабатывает до
  перерисовки). Если фокус «не переносится» — сначала проверь, не `disabled` ли
  цель в этот момент.

## Дизайн-система

Правила Nuxt UI, нарушение которых ломает единообразие:

**Только семантические цвета.** `text-default`, `text-muted`, `text-highlighted`,
`bg-default`, `bg-elevated`, `bg-muted`, `border-default`, `border-muted`.
Raw-палитра вида `text-gray-500` или `bg-slate-100` запрещена — она игнорирует
светлую/тёмную тему и смену брендинга.

**Брендинг живёт в `app/app.config.ts`**, а не в классах по компонентам. Там заданы
`primary`/`secondary`/`neutral` (сейчас indigo/violet/zinc — заготовка, а не
согласованный бренд) и дефолтные иконки. Токены `--ui-radius` и `--ui-container` —
в `app/assets/css/main.css`.

**`UApp` в `app/app.vue` обязателен** и уже стоит. Без него не работают `useToast`,
тултипы и программные оверлеи через `useOverlay`.

**Красный по умолчанию не проходит по контрасту в светлой теме.** `error-500` на
белом даёт 3.8:1 против нормы 4.5:1 для текста, поэтому в `main.css` светлая тема
переопределяет `--ui-error` на `-600` (4.8:1). Селектор `:root:not(.dark)`
обязателен: правило идёт после `@import "@nuxt/ui"` и с обычным `:root` перебило
бы и тёмную тему, где `error-400` контрастен и так.

**Подписи в навигации шапки под `sm` уходят в `sr-only`** (слот `linkLabel`), иначе
три пункта в строку вместе с логотипом не влезают в 360px и страница начинает
ездить по горизонтали. Прятать через `hidden` нельзя — подпись исчезнет и из
дерева доступности, останется кнопка без имени.

**`app.config.ts` обязан лежать внутри `srcDir`, то есть в `app/`.** Из корня
воркспейса Nuxt его не читает и молча берёт дефолты Nuxt UI (зелёный/синий/slate) —
ни ошибки, ни предупреждения. Файл уже лежал не там, поэтому indigo/violet/zinc
не применялись. Проверять так: в `.nuxt/app.config.mjs` должны быть наши цвета,
а не `"primary": "green"`.

**Не добавляй `@nuxt/icon`, `@nuxt/fonts`, `@nuxtjs/color-mode` в `modules`** —
Nuxt UI регистрирует их сам. Настраиваются корневыми ключами `icon`, `fonts`,
`colorMode` в `nuxt.config.ts`.

**Иконки** — формат `i-lucide-<name>`. Коллекция `@iconify-json/lucide` стоит
локально осознанно: `/` и `/pricing` пререндерятся, а тянуть иконки по сети во
время сборки ненадёжно.

**Приоритет переопределений** (побеждает верхнее): проп `ui` или `class` на
инстансе → `app/app.config.ts` → дефолты темы. Имена слотов компонента смотри в
сгенерированном `.nuxt/ui/<component>.ts`, а не угадывай.

**Одна solid-primary кнопка на экран.** Остальное — `variant="outline"`, `"soft"`,
`"ghost"` с `color="neutral"`. Деструктивные действия — `color="error"`.

**Hover у двух вариантов кнопок переопределён в `app.config.ts` — ради
контраста.** Дефолт Nuxt UI для solid-primary — `hover:bg-primary/75`: фон
светлеет к фону страницы, и белый текст проваливается до 3.01:1 (тёмная тема —
3.75:1) при норме 4.5:1. Вместо прозрачности — соседний оттенок той же палитры:
`primary-600` в светлой (6.46:1) и `primary-300` в тёмной (8.82:1). У
ghost-кнопки ошибки («Удалить») hover подкладывает `bg-error/10`, и красный
текст на розовом — 3.97:1; в светлой теме текст темнеет до `error-700` (5.4:1).
Правка одна на всё приложение, а не классом на инстансе: дефект — в теме, и он
одинаково задевал «Войти», «Создать аккаунт» и «К списку встреч».

**Рамки Nuxt UI не дотягивают до 3:1, и это осознанно не чинится темой.**
Токены `border`, `border-muted`, `border-accented` дают 1.19–1.7:1 в обеих
темах; так нарисованы кольца карточек, outline-кнопок и полей. У кнопок и полей
есть видимая подпись (контраст 13.96:1), и по WCAG 1.4.11 контрол опознаётся по
ней, а рамка карточки декоративна. Там, где граница — единственное, что
показывает элемент (пунктир зоны загрузки), цвет рамки берётся из `text-muted`
(6.75 / 4.83:1): `border-(color:--ui-text-muted)` в `FileDropzone.vue`.

**Локаль — `ru` у `UApp`, язык — `lang="ru"` в `app.head` `nuxt.config.ts`.** Без
локали служебные строки Nuxt UI английские посреди русского интерфейса («Switch
to dark mode», «Close»), без `lang` скринридер читает русский текст английским
голосом. `UApp` с локалью атрибут `lang` сам не ставит — только свои строки.
`aria-label="loading"` у `USkeleton` локаль не переводит, поэтому обёртка с
`aria-hidden` у скелетонов по-прежнему обязательна.

В `nuxt.config.ts` включён `ui.experimental.componentDetection` — CSS генерируется
только под использованные компоненты. Для динамических `<component :is>` имена
придётся перечислить массивом, иначе стили вырежет.

Документацию по пропсам и слотам отдаёт MCP-сервер Nuxt UI:

```bash
claude mcp add --transport http nuxt-ui https://ui.nuxt.com/mcp
```

Классы Tailwind сортирует Prettier через `prettier-plugin-tailwindcss`; настройка
лежит в корневом `.prettierrc.json` и через `tailwindStylesheet` указывает на
`apps/web/app/assets/css/main.css` — при переносе CSS-входа поправь и там.

## Главное: routeRules — это SEO-контракт

Гибридный рендеринг в `nuxt.config.ts` — причина, по которой здесь Nuxt, а не SPA
на Vite. Каждый класс маршрутов рендерится по-своему:

| Маршрут           | Режим                         | Почему                                              |
| ----------------- | ----------------------------- | --------------------------------------------------- |
| `/`               | `ssr: false` + `X-Robots-Tag` | кабинет за авторизацией, индексировать нечего       |
| `/pricing`        | `prerender: true`             | статика в `.output/public`, индексируется           |
| `/login`          | `prerender: true`             | публичная точка входа, форма оживает при гидратации |
| `/register`       | `prerender: true`             | то же                                               |
| `/blog/**`        | `isr: 3600`                   | кэш на час, страниц пока нет                        |
| `/meetings/**`    | `ssr: false` + `X-Robots-Tag` | страница встречи: файлы владельца, тот же кабинет   |
| `/profile`        | `ssr: false` + `X-Robots-Tag` | профиль вошедшего: его имя, тот же кабинет          |
| `/room/**`        | `ssr: false`                  | WebRTC и `getUserMedia` требуют браузера            |
| `/app`, `/app/**` | `redirect: '/'`               | кабинет переехал на `/`, старые ссылки не 404       |

**У корня больше нет публичной страницы.** `/` — это кабинет: раньше там лежал
пререндеренный лендинг, теперь маршрут закрыт middleware `auth` и отдаётся
клиентской оболочкой. Индексируемых страниц осталось три: `/pricing`, `/login`,
`/register`. `/meetings/**` и `/profile` — такие же приватные маршруты, как `/`,
и правило у них то же самое: `ssr: false` плюс `X-Robots-Tag`. Если понадобится
публичная витрина — это новый маршрут с `prerender: true`, а не возврат
содержимого на `/`.

**`noindex` для `/` навешен заголовком `X-Robots-Tag` в `routeRules`, а не строкой
в `robots.txt`.** `Disallow: /` закрыл бы вместе с корнем и все публичные
страницы, а `Disallow: /$` — расширение Google, не стандарт. `useSeoMeta` с
`robots: 'noindex'` на странице тоже стоит, но одного его мало: у маршрута с
`ssr: false` мета появляется только после гидратации, а робот видит оболочку.

**Каждая новая страница требует решения по routeRules.** Правило простое: публичная
и должна индексироваться — `prerender`; нужны браузерные API или авторизация —
`ssr: false`. Молча добавленная страница унаследует SSR по умолчанию, что для
комнаты со звонком означает падение на серверном рендере.

**`prerender: true` на маршруте без страницы ломает сборку** — пререндер получает
404 и валит `nuxt build`. Правило и страницу заводи вместе.

Проверить, что разделение живо, после `bun run build`:

```bash
ls apps/web/.output/public      # ожидаем pricing/, login/ и register/
```

`/`, `/meetings/**`, `/profile`, `/room/**` и `/app/**` в `.output/public`
попадать не должны — они отдаются клиентской оболочкой. Быстрая проверка на
запущенном сервере: у `/pricing` в HTML есть `<h1>`, у `/`, `/profile` и
`/room/abc` — нет.

## Метаданные

На публичных страницах — `useSeoMeta` с `title` и `description` (уезжают в
пререндеренный HTML). На приватных — `robots: 'noindex'`; вдобавок
`public/robots.txt` закрывает `/room/`, а `/` — заголовком `X-Robots-Tag` из
`routeRules` (почему не через `robots.txt` — в разделе про routeRules). Все места
надо держать согласованными.

## Браузерные API

Всё, что трогает `window`, `navigator.mediaDevices`, WebRTC, живёт либо на маршруте
с `ssr: false`, либо под `import.meta.client` / `onMounted` / `<ClientOnly>`.
На SSR-маршруте обращение к `window` на верхнем уровне `<script setup>` уронит рендер.

## Конфигурация и типы

Адрес API берётся из `useRuntimeConfig().public.apiUrl`, а не из `import.meta.env`.
Переопределяется переменной `NUXT_PUBLIC_API_URL` — Nuxt сопоставляет её с
`runtimeConfig.public.apiUrl` по имени.

Авто-импорты Nuxt (`ref`, `computed`, `useRoute`, `useSeoMeta`, компоненты из
`app/components/`) не надо импортировать вручную. Из-за них в корневом ESLint-конфиге
для `apps/web` выключены два правила:

- `no-undef` — авто-импорты для него не существуют, а реальные опечатки всё равно
  ловит `vue-tsc` по типам из `.nuxt`;
- `vue/multi-word-component-names` для `pages/` и `layouts/` — имена там диктует
  файловый роутинг (`index.vue`, `pricing.vue`).

`tsconfig.json` ссылается на сгенерированные `.nuxt/tsconfig.*.json`, поэтому
**typecheck без `.nuxt` не работает**. Папку создаёт `nuxt prepare`, он же висит в
`postinstall`. Если typecheck жалуется на отсутствующие пути или незнакомые
авто-импорты — первым делом пересобери типы:

```bash
cd apps/web && bun run nuxt prepare
# либо из корня:
bun run --filter @video-meetings/web postinstall
```

## Авторизация: вход, регистрация и кабинет

Сквозной контур — `/login` → `/` и `/register` → `/`, из кабинета ссылка
«Профиль» ведёт на `/profile`, где задают имя, ставят аватар и меняют пароль. Страницы только
оркестрируют, логика и разметка живут по краям.

| Файл                                           | Ответственность                                                                                                             |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `app/pages/login.vue`                          | вызов `login()`, тост, редирект на `/`, состояние отправки                                                                  |
| `app/pages/register.vue`                       | то же для `register()`                                                                                                      |
| `app/pages/index.vue`                          | кабинет: загрузка, разбор 401, выход, разбивка встреч по блокам                                                             |
| `app/pages/profile.vue`                        | профиль: загрузка `/auth/me`, алерт с «Повторить», разбор 401, имя, аватар (проверка до отправки, удаление), пароль, тосты  |
| `app/components/profile/NameForm.vue`          | блок «Имя»: state, валидация, текст отказа под полем, фокус, поле после сохранения                                          |
| `app/components/profile/AvatarForm.vue`        | блок «Аватар»: круг, «Загрузить»/«Заменить», «Удалить», скрытый `input`, подсказка или отказ, фокус после запроса           |
| `app/components/profile/DeleteAvatarModal.vue` | подтверждение удаления аватара для `useOverlay`, результат — `close(boolean)`                                               |
| `app/components/profile/PasswordForm.vue`      | блок «Пароль»: три поля, валидация, отказ api под своим полем, фокус, пустая форма после смены                              |
| `app/components/auth/CredentialsForm.vue`      | одна форма на вход и регистрацию: state, валидация, ошибки, фокус                                                           |
| `app/components/auth/RegisterAside.vue`        | левая колонка на `/register`, без логики                                                                                    |
| `app/components/dashboard/AccountCard.vue`     | аватар, имя и адрес вошедшего, ссылка «Профиль», кнопка «Выйти»                                                             |
| `app/components/meetings/*`                    | `MeetingsSection` — блок с заголовком, `MeetingItem` — строка со ссылкой на встречу, `MeetingCard` — карточка одной встречи |
| `app/composables/useAuth.ts`                   | кука с токеном, общий `user`, `/auth/*`, `handleUnauthorized` — разбор 401 на всех страницах за авторизацией                |
| `app/composables/useMeetings.ts`               | `GET /meetings` и `GET /meetings/:id`                                                                                       |
| `app/middleware/auth.ts`                       | guard приватных страниц                                                                                                     |
| `app/utils/api.ts`                             | `statusOf`, `isUnauthorized`, текст «нет связи»                                                                             |
| `app/utils/auth.ts`                            | границы полей, проверка формы смены пароля и разбор отказов `/auth/*`                                                       |
| `app/utils/meetings.ts`                        | разбивка на блоки, формат даты, множественные формы                                                                         |
| `app/utils/profile.ts`                         | копия правил имени и лимитов аватара с api, тексты ошибок, разбор отказов профиля                                           |

Неочевидности:

- **Форма на входе и регистрации одна.** Различия сведены к пропсам
  (`submitLabel`, `passwordAutocomplete`, тексты подсказок); всё остальное —
  валидация, перенос фокуса, объявление ошибок — общее. Две копии означали бы
  починенную доступность в одной и забытую в другой: правки ниже стоили
  отдельного прогона в браузере каждая.
- **Текст «пустой пароль» выводится из `passwordAutocomplete`, а не из своего
  пропа.** `new-password` — это и есть «регистрация» («Придумайте пароль»),
  `current-password` — «вход» («Введите пароль»). Второй флаг о том же разъехался
  бы с первым. Само сообщение приходит в `validateCredentials` параметром: сначала
  общий текст показывал на входе «Придумайте пароль».
- **Границы полей продублированы с api и должны меняться вместе.** Константы в
  `app/utils/auth.ts` (пароль 8..128, адрес до 254) повторяют схемы из
  `apps/api/src/modules/auth.ts`; граница пароля там одна у регистрации, входа и
  смены пароля (`POST /auth/me/password`). Разъезд не поймают ни
  типы, ни сборка: форма начнёт отправлять то, что api отвергает 422-м, либо
  наоборот отбивать годное.
- **Валидация без schema-библиотеки.** `UForm` принимает Standard Schema (zod,
  valibot), но здесь передана функция `:validate` — ради двух полей зависимость не
  ставилась. Форма смены пароля правил почти не добавила: та же граница пароля
  (одна функция `checkPassword` на все формы) и сверка повтора. Появится форма с
  нетривиальными правилами — есть смысл взять zod и переписать валидаторы
  схемами, а не наращивать `if`-ы.
- **Отказ api приезжает в форму пропсом, а не через template ref.** `AuthFailure`
  с полем `field` уходит в `:error` нужного `UFormField`, без него — в `UAlert` над
  формой. Поэтому странице не нужен ни `form.setErrors`, ни ссылка на компонент.
- **401 на входе не подсвечивает поле.** Api намеренно отвечает одинаково на
  неизвестный адрес и на неверный пароль, чтобы по ответу не перебирали
  зарегистрированные адреса. Указать на конкретное поле значило бы додумать за
  api то, чего он не говорил, — поэтому текст уходит в алерт над формой.
- **Токен лежит в куке `auth_token`, а не в `localStorage`.** Куку видит и сервер,
  поэтому middleware отбивает неавторизованного до рендера. `maxAge` — 7 дней,
  ровно как `JWT_EXPIRES_IN` на api: меняешь там — меняй здесь.
- **Адрес вошедшего берётся у `GET /auth/me`, а не из payload'а токена.**
  Раскодировать JWT на клиенте можно, но форма payload'а не зафиксирована
  контрактом, а подпись без секрета всё равно не проверить. Проверено в браузере:
  вход под `ORGANIZER@example.com` показывает в кабинете `organizer@example.com` —
  адрес пришёл из базы нормализованным, а не из формы.
- **`user` держится в `useState`, а не в локальном ref композабла.** `useAuth()`
  вызывается и на странице, и в middleware; с локальным состоянием каждый вызов
  получал бы своего пользователя и свой запрос `/auth/me`.
- **Middleware проверяет только наличие куки — и это не упущение.** Годность
  токена подтверждает api: разобрать `exp` на клиенте можно, но подпись без
  секрета не проверить, так что настоящий рубеж — 401. Кабинет, профиль и
  страница встречи разбирают его одним хелпером `handleUnauthorized` из
  `useAuth` — и на загрузке, и на действиях. Это конец сессии (тост, `logout()`,
  `/login`), а не сбой запроса, иначе истёкший токен показывал бы «попробуйте
  ещё раз» без выхода из тупика, — если только в куке уже не другой токен, чем
  ушёл с запросом: тогда запрос повторяется с ним (почему — ниже).
- **401 перечитывает куку перед выходом, потому что кука одна на все вкладки.**
  Смена пароля отзывает на api все прежние токены пользователя, а вкладка,
  сменившая пароль, кладёт новый в общую куку. Соседняя вкладка, чей запрос
  ушёл со старым токеном до смены, получает 401, хотя сессия жива, — и
  `logout()` стёр бы из куки уже новый токен, выкинув из системы обе вкладки.
  Это и воспроизвёл прогон фазы 3 на коде до хелпера. Поэтому
  `handleUnauthorized` сравнивает токен, с которым ушёл запрос (`sentToken`,
  снятый страницей перед запросом), с тем, что лежит в куке сейчас: другой —
  повтор, тот же или пусто — выход. Проверять «есть ли кука» мало: мёртвый
  токен в ней тоже лежит, и с ним страница повторяла бы запрос по кругу. Повтор
  не зацикливается: его 401 приходит с токеном из куки и кончается выходом.
- **Токен для запроса читается из `document.cookie`, а не из ref'а
  `useCookie`** (`currentToken` в `useAuth`). Ref у каждого вызова `useAuth()`
  свой — у страницы, `useMeetings`, `useMeetingFiles`, — и запись соседней
  вкладки он догоняет событием `cookieStore`, не синхронно. Возьми хелпер новый
  токен в ref страницы, повтор `fetchMeetings` ушёл бы со старым из ref'а
  `useMeetings`, получил второй 401 и всё-таки вышел. Кука общая, поэтому
  повтор несёт новый токен по построению. Пишется кука по-прежнему через ref:
  watcher `useCookie` кладёт значение в `document.cookie` до ближайшей
  перерисовки, задолго до следующего запроса.
- **Неверный текущий пароль приходит 403, а не 401** — и 400 на «новый совпадает
  с текущим» тоже не 401. Здесь 401 значит «сессия кончилась»: его разбирает
  `handleUnauthorized`, и при неизменной куке это выход. Отвечай api на
  опечатку в поле 401-м, она выкидывала бы пользователя на `/login` вместо
  текста под полем. Правило общее: 401 — только про негодный токен; отказ по
  содержимому формы под живым токеном приходит другим кодом. Появится маршрут,
  который отвечает 401 на что-то ещё, — эта ветка выйдет из системы там, где не
  надо.

Имя на профиле и в карточке:

- **Правила имени продублированы с api, как границы `credentials`.**
  `validateName` в `app/utils/profile.ts` повторяет шаблон `nameUpdate` из
  `apps/api/src/modules/auth.ts`: управляющие символы (Cc, `U+2028`, `U+2029`) —
  отказ где угодно, длина — до 50 после `trim()`, в UTF-16 code units, пустое —
  годно, это сброс. Сначала управляющие, потом обрезка: отсеяв их, `trim()`
  срезает ровно те пробелы, что и шаблон api. Проверка — кодами символов, а не
  регуляркой: класс с `\u0000` запрещает правило `no-control-regex`. Строка
  уходит на api как набрана — обрезает и сбрасывает в `null` сам api.
- **Любой отказ сохранения, кроме 401, — текстом под полем, а не алертом.** Поле
  в блоке одно, так что «не сохранилось» всегда про него, а строка `help` под
  ним существует заранее, и текст встаёт на её место без сдвига. Отсюда же
  ограничение: подсказка и все тексты ошибок — в одну строку на 360px (под полем
  281px), иначе вторая строка сдвинула бы кнопку на 20px. Поэтому «нет связи»
  у имени свой, короче общего `NO_CONNECTION_MESSAGE` (312px): тот живёт в
  алертах и тостах, где места хватает. Бюджет был 296px, пока страница
  помещалась в экран: с блоком «Пароль» она прокручивается и на 360×800, а
  обычная полоса прокрутки Chrome съедает 15px. Подсказка «До 50 символов.
  Пустое поле — без имени.» (282px) от этого переехала на вторую строку, и
  блок стал на 20px выше своего скелетона, — теперь она короче (247px).
- **После сохранения поле показывает ответ api, а не набранное.** Форма
  сверяется с сохранённым именем по концу запроса (`loading` true → false), а
  не по `watch(() => props.name)`: « Анна » поверх «Анна» имя не меняет, и
  пробелы остались бы в поле. Фокус, уехавший в `body` с выключенных на время
  запроса поля и кнопки, возвращается туда, где был при отправке (Enter в поле
  или клик по кнопке); на отказе — в поле, к тексту ошибки.
- **Ответ `PATCH /auth/me` сразу ложится в общий `user`.** Поэтому карточка на
  `/` после перехода по ссылке показывает новое имя ещё до своего `/auth/me`, и
  ни перезагрузка, ни второй запрос ради этого не нужны.
- **Имя в карточке — `text-base/5` и `wrap-anywhere`.** Строка 20px, как у
  `text-sm`: карточка с именем той же высоты, что без него и что заглушка, и
  список встреч не прыгает. `overflow-wrap: anywhere`, а не `break-words`:
  только он уменьшает min-content, и 50 букв без пробела на 360px не распирают
  карточку. Имя выводится интерполяцией, так что `<b>Анна</b>` — текст.
- **В тосте об успехе самого имени нет.** Что сохранилось, показывает поле, а
  50 букв без пробела вылезали из тоста за край экрана на 360px.

Пароль на профиле:

- **Три поля, у каждого `help`, и все тексты — в одну строку на 360px**, по
  тому же правилу, что у имени: строка под полем существует заранее, и ошибка
  встаёт на её место. Самый длинный текст — подсказка «От 8 до 128 символов,
  не как текущий» (246px из 281). `autocomplete` — `current-password` у
  текущего и `new-password` у нового и повтора: по нему менеджер паролей
  подставляет сохранённый и предлагает сгенерировать новый.
- **Скрытое поле `username` с адресом вошедшего.** Без него Chrome пишет в
  консоль «Password forms should have (optionally hidden) username fields», а
  менеджер паролей не знает, у какой учётки сохранить новый пароль. `hidden`
  убирает поле и из обхода Tab'ом, и из дерева доступности.
- **Совпадение нового с текущим клиент не проверяет**, хотя оба поля под рукой.
  Api сверяет его только после текущего пароля: на неверный текущий, совпавший
  с новым, ответ «совпадает с текущим» был бы неправдой, и клиентская проверка
  соврала бы так же. Поэтому этот отказ приходит 400-м и встаёт под «Новый
  пароль», а 403 «Текущий пароль неверен» — под «Текущий пароль»; оба текста
  api показываются как есть. Остальные отказы (422, 5xx, нет связи) — про
  запрос целиком и уходят тостом: в форме из трёх полей им нет своего места, а
  тост не сдвигает вёрстку. Введённое при этом остаётся для повтора.
- **Отказ api по полю живёт в форме отдельно от ошибок `UForm`** и отдаётся в
  проп `error` у `UFormField`, а не через `setErrors`. В ошибки `UForm` пишет
  и отложенная на 300 мс проверка поля по вводу: ответ api приходит быстрее, и
  она его стирала — замер: 400 под «Новым паролем» появлялся и через 220 мс
  пропадал. Текст отказа держится, пока в поле то значение, которое api
  отверг: правка снимает его, и под полем снова подсказка.
- **После смены форма собирается заново (`:key`), а не очищается.** У прежней
  могла остаться отложенная проверка по вводу, и через 300 мс после ответа она
  пометила бы уже пустое поле «Введите текущий пароль». Размонтированное поле
  свою проверку отменяет, а новая форма не помнит, какие поля трогали. Фокус
  возвращается туда, где был при отправке, — по имени поля, раз прежнего
  элемента в DOM уже нет.
- **`validate-on` без `blur`.** Блок необязательный: пройти Tab'ом по пустым
  полям — не ошибка, и после смены пароля пустые поля не должны краснеть,
  стоит из них уйти. Поле проверяется, когда его поменяли (`change`, `input`
  после первого ухода), и вся форма — на отправке.
- **Повторная отправка, пока запрос в полёте, не уходит.** Выключенные поля и
  кнопка этого не гарантируют: `UForm` валидирует асинхронно, и два `submit`
  подряд проходят проверку раньше перерисовки. Без флага на странице два
  `requestSubmit()` подряд дают два `POST` — оба 200, — а на api две
  одновременные смены проходят обе, и токен первой отзывает вторая: пришёл бы
  её ответ последним — в куке остался бы мёртвый токен. Флаг ставится до
  первого `await`, поэтому второй вызов видит его всегда.
- **Кнопка «Сменить пароль» — `outline` и `neutral`.** Одна solid-primary на
  экран уже есть — «Сохранить» у имени.

Аватар на профиле и в карточке:

- **Отказ — текстом под кнопками, на месте подсказки, и место под две строки
  есть всегда** (`min-h-10`). В одну строку на 360px тексты api не влезают:
  «Подходят только изображения JPEG, PNG и WebP» и «Изображение пришло не
  целиком — загрузите его ещё раз» шире 281px, а менять их нельзя — они
  повторяют api слово в слово. Поэтому подсказка сама в две строки («JPEG, PNG
  или WebP, до 2 МБ.» и «Неквадратное фото обрежется по кругу.»), и отказ
  любой длины до двух строк встаёт на её место без сдвига. Тост, как у файлов
  встречи, тоже не сдвигал бы вёрстку, но исчезает через секунды, а причина
  отказа нужна рядом с кнопкой, которой выбирают следующий файл.
- **Строка отказа — `role="alert"` с ключом по номеру выбора файла.** Два GIF
  подряд дают один и тот же текст: без нового ключа Vue не перерисовал бы
  элемент, и скринридер не объявил бы второй отказ. С кнопкой строка связана
  `aria-describedby` — подсказку или отказ слышно и при заходе на кнопку.
- **Файл выбирает скрытый `input`, открывает его кнопка.** После выбора
  `value` сбрасывается: иначе повторный выбор того же файла (после отказа или
  обрыва связи) не дал бы `change` — та же ловушка, что была у зоны загрузки
  файлов встречи.
- **Фокус после запроса возвращается на кнопку блока.** Пока запрос шёл, кнопки
  были выключены, и фокус уехал в `body`. После удаления «Удалить» уже нет, и
  фокус встаёт на «Загрузить»; Reka, закрывая диалог, вернул бы его на
  исчезнувший триггер, то есть в никуда.
- **Одно действие с аватаром за раз.** `avatarBusy` (`'upload'`, `'delete'`
  или `null`) ставится до первого `await`, обе кнопки на это время выключены, а
  второй клик по «Удалить», пока диалог открыт, его заново не открывает.
- **Кнопки — `outline`/`neutral` и `ghost`/`error`.** Solid-primary на экране
  одна — «Сохранить» у имени. На 360px «Заменить» и «Удалить» встают в два
  ряда (72px) и помещаются в высоту круга (80px): строка не растёт, когда
  кнопка «Удалить» появляется.
- **Отказы 413, 415 и 400 — текстом api**, как у файлов встречи
  (`describeAvatarUploadFailure`): обычно такой файл до api не доезжает, но
  `.png` с чужим содержимым отобьёт только api.
- **`avatarUrl` — путь, и `<img>` получает его через `apiHref`** — и в блоке
  профиля, и в `AccountCard`, как ссылку на файл встречи. Вставленный как есть,
  путь ушёл бы на origin фронтенда и получил 404 от Nuxt. Новый аватар виден
  сразу без всякого сброса кэша: у него другой ключ в адресе, а ответ загрузки
  и удаления уже лежит в общем `user` — на `/` карточка показывает его ещё до
  своего `/auth/me`.
- **Текстовая альтернатива — имя, без имени — адрес**, то есть то, что
  карточка показывает крупно рядом с кругом. Без аватара или с битой ссылкой
  (замена в соседней вкладке, старый адрес отвечает 404) `UAvatar` сам рисует
  иконку-заглушку.
- **Размеры `<img>` заданы атрибутами**: `UAvatar` ставит `width` и `height` по
  классу `size-*` своего корня — 80 на профиле (`class="size-20"` перекрывает
  размер по умолчанию), 36 в карточке. Круг фиксированного размера, и
  пришедшая картинка ничего не сдвигает.

### Что проверено в браузере

Прогон по состояниям, а не только по «счастливому» виду (все цифры — замеры):

| Состояние             | Что подтверждено                                                      |
| --------------------- | --------------------------------------------------------------------- |
| `/` без токена        | редирект на `/login`, запросов к api ноль                             |
| пустая отправка формы | `aria-invalid`, `aria-describedby`, фокус в первое поле, сдвиг 0px    |
| 401 на входе          | `role="alert"`, фокус на кнопку, поля не помечены ошибочными          |
| негодный токен в куке | тост «Сессия истекла», кука очищена, редирект на `/login`             |
| api не запущен        | алерт «Нет связи с API» с кнопкой «Повторить», карточка не в загрузке |
| api вернулся          | «Повторить» подтягивает и адрес, и встречи без перезагрузки           |
| выход                 | кука удалена, кнопка «Назад» кабинет не открывает                     |
| пустой список         | заглушка без лишнего заголовка, счётчик «0 встреч»                    |

Три ловушки, найденные этим прогоном:

- **`USkeleton` навешивает на каждый экземпляр `role="alert"`, `aria-live="polite"`
  и `aria-label="loading"`.** Восемь заглушек на загрузке кабинета давали восемь
  конкурирующих живых регионов, объявляющих чужое английское слово. Лечится
  обёрткой с `aria-hidden="true"` — предок выключает всё поддерево разом, — а о
  загрузке сообщает один `role="status"` со своим текстом. Ставить атрибуты на сам
  `USkeleton` бессмысленно: `role` он задаёт сам.
- **`title` у `UEmpty` рендерится жёстко как `<h2>`.** Внутри секции с таким же
  `<h2>` получалась вторая равноправная секция — заголовок ради оформления
  статуса. Поэтому пустое состояние передаётся одной строкой в `description`.
- **`text-dimmed` не проходит по контрасту для содержательного текста.** «Без
  участников» давало 2.62:1 против нормы 4.5:1; `text-muted` — 4.83:1 в светлой
  теме и 6.75:1 в тёмной. `dimmed` годится для декора, не для данных.

Плюс две правки за пределами кабинета: у логотипа в шапке не было индикатора
фокуса (голый `NuxtLink`, в отличие от `UButton`, своего не имеет), а он первая
остановка Tab на каждой странице — добавлен `focus-visible:outline-2` с контрастом
4.58:1. И пункты меню в шапке остались статичными и публичными: собранное по куке
меню разошлось бы между пререндеренным HTML, где токена нет, и гидратацией — кто
вошёл и кнопка выхода живут на самой странице кабинета.

Доступность формы держится на четырёх правках, каждая из которых снимает
конкретный замер (все цифры — из прогона в браузере):

- **`novalidate` на `UForm`.** Без него браузер сам валидирует `type="email"` и
  показывает свой пузырь раньше нашего сообщения: два разных текста об одной
  ошибке, и побеждает браузерный — вместе с ним теряется и перенос фокуса.
- **`:loading-auto="false"` плюс `flush: 'post'` у watcher'а.** Оба про одно: пока
  форма считается отправляемой, поля выключены, а `focus()` на disabled-инпуте
  молча ничего не делает. `loadingAuto` выключал поля на время валидации, а
  watcher по умолчанию срабатывает до перерисовки — фокус улетал в никуда.
  Блокировку на время запроса держит проп `loading` со страницы.
- **Фокус после неудачной отправки.** `@error` ставит курсор в первое поле с
  ошибкой, отказ api с полем — туда же, отказ уровня запроса возвращает фокус на
  кнопку. Иначе Tab начинал обход страницы с начала, а о самих ошибках
  скринридер не сообщал: `aria-describedby` объявляется только при заходе в поле.
- **`role="alert"` на `UAlert`.** Единственный способ объявить «нет связи с API»:
  живого региона у `UAlert` по умолчанию нет.

Две мелочи из того же прогона: у обоих полей стоит `required` (у `UFormField` он
рисует звёздочку, но `aria-required` на инпут не ставит), а `help` есть у каждого
поля на обеих формах — не для красоты, а чтобы строка под полем существовала
заранее. `UFormField` подменяет `help` текстом ошибки, а не добавляет его рядом,
так что при готовой строке сдвиг равен нулю — это и замерено на пустой отправке.

### Что проверено в браузере (профиль, фаза 1)

Прогон Playwright MCP, Chrome, пользователь заведён формой регистрации; все
цифры — замеры:

| Проверка                           | Что подтверждено                                                                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| «Анна Петрова» → «Все встречи»     | `PATCH /auth/me` 200, карточка «Анна Петрова» и адрес под ним; документ тот же (метка на `window` жива, журнал запросов не сброшен)        |
| `"  " + 50 букв + "  "` и 51 буква | первое сохраняется — граница после обрезки; второе — «Не длиннее 50 символов — сейчас 51», `aria-invalid`, фокус в поле, `PATCH` ни одного |
| табуляция в имени                  | «Без табуляции и служебных символов», `PATCH` ни одного                                                                                    |
| `<b>Анна</b>`                      | в карточке текстом: `&lt;b&gt;Анна&lt;/b&gt;`, элементов `<b>` в `main` — 0                                                                |
| пустое поле                        | «Имя сброшено», карточка снова — адрес и «Аккаунт организатора»                                                                            |
| 422, 500, обрыв связи (подмена)    | текст под полем в одну строку (20px), фокус в поле, сдвиг кнопки 0px на 360 и 1280                                                         |
| 401 на сохранении, негодный токен  | тост «Сессия истекла», кука очищена, `/login`                                                                                              |
| api недоступен на загрузке         | `role="alert"` «Профиль не загрузился» с «Повторить»; после возврата данные приходят без перезагрузки                                      |
| `/profile` без куки                | `/login`, запросов к `:3000` в журнале ноль — и среди статических                                                                          |
| загрузка                           | один `role="status"`; скелетон и готовый блок одной высоты: 216/216px на 360, 232/232px на 1280                                            |
| 360 и 1280, обе темы               | `scrollWidth === clientWidth` (и с именем из 50 букв), текст 4.83–17.72 / 6.75–17.72:1, иконка 4.58 / 5.66:1, цели 107×32 и 88×32          |

Найденное этим прогоном, кроме уже описанного выше тоста с именем:

- **Текст тоста в DOM дважды.** Reka кладёт копию во скрытый `role="alert"` с
  `aria-live="assertive"` — так тост и объявляется скринридеру. Поэтому
  `getByText('Имя сохранено')` в Playwright падает на strict mode; искать надо
  `li [data-slot="title"]`. Это не дубль на экране и не дефект.
- **После перезапуска `bun run dev` первая загрузка страницы перезагружается
  Vite'ом** (оптимизация зависимостей), и уже заполненная форма теряется: первый
  вход в прогоне ушёл в никуда без ошибки и без запроса. Если клик по «Войти» не
  дал запроса — повторить после загрузки, а не искать дефект в форме.
- **Журнал `browser_network_requests` не сбрасывается при клиентском переходе,**
  а метка на `window` переживает его: вместе это и есть доказательство «без
  перезагрузки». В `browser_run_code_unsafe` нет `require` — сохранить что-то в
  файл оттуда нельзя.

### Что проверено в браузере (профиль, фаза 3)

Прогон Playwright MCP, Chrome, пользователь заведён формой регистрации. «Другое
устройство» — кука, подменённая на токен, сохранённый до смены; «вторая
вкладка» — вторая страница того же контекста, кука у вкладок общая. Все цифры —
замеры:

| Проверка                                       | Что подтверждено                                                                                                        |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| повтор не совпал                               | «Не совпадает с новым паролем», `invalid` и фокус у повтора; в журнале запросов только `GET /auth/me` загрузки страницы |
| неверный текущий пароль                        | `POST /auth/me/password` 403, «Текущий пароль неверен» под полем, фокус в нём, кука прежняя, страница `/profile`        |
| новый равен текущему                           | 400, «Новый пароль совпадает с текущим» под «Новым паролем» и держится дольше 300 мс                                    |
| успешная смена                                 | 200, кука сменилась (`Max-Age` 7 дней, `Lax`, `/`), поля пустые, через 1.5 с ни одной ошибки, тост; перезагрузка — 200  |
| двойной клик, два Enter, два `requestSubmit()` | по одному `POST`; без флага на странице два `requestSubmit()` — два `POST`, оба 200                                     |
| 500, 422, обрыв связи (подмена)                | тост «Пароль не изменён» с текстом, фокус на кнопке, введённое на месте                                                 |
| кука с токеном до смены                        | на `/`, `/profile`, `/meetings/[id]` — 401, тост «Сессия истекла», кука удалена, `/login`; каждый запрос — один раз     |
| вторая вкладка меняет пароль, первая — ссылка  | первая без перезагрузки уходит на `/` — `/auth/me` и `/meetings` 200, та же страница; вторая после этого — 200          |
| то же, первая жмёт «Повторить»                 | первая показывала «Профиль не загрузился» (подмена обрыва); «Повторить» — 200 с новым токеном, `PATCH` во второй — 200  |
| запрос первой ушёл до смены, ответ после       | 401 → кука уже другая → повтор → 200 на `/`, `/profile` (загрузка и сохранение имени) и `/meetings/[id]`                |
| тот же сценарий до хелпера (`92e548e`)         | 401, 401 → кука удалена → `PATCH` во второй вкладке 401 → обе на `/login`: баг из PRD воспроизведён                     |
| загрузка и скелетоны                           | один `role="status"`; скелетон = блок: «Имя» 260/260, «Пароль» 476/476 на 360; 276/276 и 492/492 на 1280                |
| 360 и 1280, обе темы                           | `scrollWidth === clientWidth`, сдвиг кнопки и полей при ошибках 0px, текст 4.77–17.72 / 6.13–17.72:1, глаз 28×28        |

Найденное этим прогоном, кроме уже описанного в «Пароль на профиле»:

- **Устаревшая вкладка в Chrome сама догоняет куку.** Nuxt 4.5 включает
  `experimental.cookieStore` по умолчанию, и ref `useCookie` получает запись
  соседней вкладки событием `cookieStore`. Поэтому сценарий «пароль сменили во
  второй вкладке, первая потом делает запрос» проходил и до хелпера — запрос
  уходил уже с новым токеном. Ломался другой: запрос ушёл со старым токеном, а
  401 пришёл после смены. Его воспроизводит только задержка: `page.route` в
  первой вкладке держит её `GET`, пока вторая меняет пароль. Без задержки
  проверка зелёная при любом коде и ничего не проверяет.
- **Обработчики `page.route` переживают вызов `browser_run_code_unsafe`.**
  Оставленный прошлым вызовом обработчик с неотпущенным ожиданием перехватил
  запрос следующего, и тот упал на «Route is already handled!». Перед новой
  подменой — `page.unrouteAll({ behavior: 'ignoreErrors' })`.
- **Снапшот показывает значение поля пароля открытым текстом**
  (`textbox "Текущий пароль*": phase3-password-12`). Это Playwright читает
  `value`, на экране поле по-прежнему `type="password"` — не дефект.
- **Звёздочка обязательного поля входит в доступное имя** — «Текущий
  пароль*». `UFormField` с `required` рисует её через `after:content-['*']`, а
  содержимое `::after` по спецификации accname попадает в имя. Так же и на
  входе и регистрации; в этой фазе не чинилось.

| `app/types/files.ts`, `app/utils/files.ts` | контракт файла, копия лимитов api, форматы размера и даты, тексты           |

Неочевидности:

- **Имя файла уезжает заголовком `X-File-Name` и обязано быть percent-encoded.**
  Тело запроса занято самими байтами: api не парсит его и сливает на диск
  потоком. Значение HTTP-заголовка — это байты Latin-1, поэтому
  `setRequestHeader('x-file-name', 'Отчёт.pdf')` бросает `TypeError` прямо в
  браузере. `encodeURIComponent` здесь и `decodeURIComponent` на api — такой же
  дублированный контракт, как границы `credentials`: разъезд не поймают ни типы,
  ни сборка.
- **Отправка — `XMLHttpRequest`, а не `$fetch`.** Ни ofetch, ни `fetch` не
  сообщают о переданных байтах (у `fetch` с телом-потоком в Chrome нужен
  HTTP/2), а без них процент показать нечем. `upload.onprogress` даёт процент,
  `abort()` — отмену, которая доходит до api: соединение рвётся, и api сам
  удаляет недописанный `.part`. Отказ XHR заворачивается в `UploadError` с
  `statusCode` и `data` — той же формы, что у ofetch, поэтому `statusOf`,
  `isUnauthorized` и `apiMessageOf` разбирают его без отдельной ветки.
- **После 100 % подпись меняется на «Сохраняем файл на сервере…».** Процент
  считает байты, ушедшие в сокет, а не записанные на диск: для большого файла
  ответ api приходит заметно позже, и застывшие «100 %» читаются как зависание.
  Полоса в этой фазе бегущая, без значения, — сколько ждать, клиент не знает.
- **Проверка до отправки — копия контракта api.** Списки расширений, лимиты и
  тексты отказов в `app/utils/files.ts` повторяют
  `apps/api/src/modules/files/limits.ts`, как границы `credentials`: разъезд не
  поймают ни типы, ни сборка. На отказе на api не уходит ни одного запроса.
  Заявленный тип не проверяется: браузер берёт его из реестра ОС и часто
  оставляет пустым, подмену отобьёт api.
- **`accept` у зоны — только расширения, без MIME-типов.** С MIME-типами
  `UFileUpload` фильтрует ещё и перетаскивание (`useDropZone` с `dataTypes`), и
  брошенный `.zip` молча пропадал бы вместо внятного отказа. Расширения
  `parseAcceptToDataTypes` пропускает, так что они работают только подсказкой
  диалогу.
- **Дроп нескольких файлов берёт первый, и об этом говорит тост.** Сам
  `UFileUpload` при `multiple: false` молча берёт первый. Сколько бросили,
  `FileDropzone` считает в фазе захвата на своей обёртке — раньше обработчика
  компонента. На сам `UFileUpload` слушатель повесить нельзя: у него
  `inheritAttrs: false`, и атрибуты уезжают на скрытый `input`.
- **`reset` и `:model-value="null"` у зоны.** Выбранный файл нужен один раз, на
  отправку, поэтому компонент его не держит, а `reset` очищает скрытый `input`
  при каждом открытии диалога. Без этого повторный выбор того же файла (после
  отказа или обрыва) не давал `change`, и не происходило ничего.
- **Пока файл уезжает, на месте зоны — его строка.** Второй файл параллельно
  всё равно не принимается (очереди в этой итерации нет), а одна площадь не
  прыгает между «зона» и «зона плюс строка». Встреча заполнена — вместо зоны
  объяснение, а не приглашение выбрать файл ради отказа.
- **Список после загрузки не перезапрашивается.** Api возвращает метаданные
  ровно этого файла (с готовой ссылкой `url`), а сортировка по дате загрузки
  ставит его в конец — туда же, куда его дописывает страница.
- **Ссылка на файл — путь от корня api, и склеивается с `apiUrl` в `apiHref`.**
  Вставленный в `<video src>` как есть, путь ушёл бы на origin фронтенда и
  получил 404 от Nuxt. Склейка строкой, а не `new URL(path, apiUrl)`: путь с
  ведущим слэшем отбросил бы префикс у адреса вида `https://host/api`.
- **Токен в ссылке живёт 15 минут, и у плеера и скачивания разные лекарства.**
  `useFreshLinks` тихо перезапрашивает список, когда ссылкам больше 10 минут, —
  по минутному таймеру и при возврате на вкладку (таймер засыпает вместе с
  ней). Это спасает «Скачать»: обычная `<a href>` с протухшим токеном увела бы
  пользователя на голый JSON 401. Плеер так не спасти — запись, открытая
  20 минут назад, ловит `error` на элементе (401 от api `<video>` не отличает
  от битого файла) и просит свежий список; второй отказ подряд — уже
  сообщение, а не новый запрос, иначе на битом файле был бы цикл.
- **Плеер держит снимок адреса, а не живой `href`.** Иначе тихий перезапрос
  списка подменял бы `src` и перезапускал запись посреди просмотра. Новый адрес
  плеер берёт только после своей ошибки.
- **Перезапрос не затирает свежие правки списка.** Список меняют загрузка
  страницы, свой файл (загрузка, удаление) и тихий перезапрос; версия списка
  (`listVersion`) отбрасывает ответ перезапроса, если за время запроса список
  поменялся, — иначе только что загруженный файл мог пропасть до следующего
  обновления. Не применённый ответ не сбрасывает отсчёт, и таймер попробует
  снова.
- **«Скачать» — обычная ссылка, а не кнопка со скриптом.** Атрибут `download`
  на кросс-origin ссылке (5173 → 3000) браузер игнорирует, имя файла приезжает
  из `Content-Disposition` api, а ответ с `attachment` навигацию не совершает —
  страница остаётся на месте. Проверять надо результат скачивания, а не
  разметку.
- **Плеер только у записей и только по кнопке.** `preload="metadata"`, без
  автозапуска; у `<video>` — `aspect-video`, чтобы место было зарезервировано до
  метаданных и строка не толкала список. Кнопка «Смотреть»/«Слушать» — с
  `aria-expanded` и `aria-controls`, у самого элемента — `aria-label` с именем
  файла.
- **Удаление — через `useOverlay` и `await result`.** Подтверждение читается как
  обычный `await`, без флагов «открыт ли диалог». У диалога нет крестика: первым
  фокус получает «Отмена», и случайный Enter файл не удалит. После удаления
  строка исчезает вместе с кнопкой, поэтому фокус уходит на заголовок блока
  (`focusHeading` из `FilesSection`), а не в `body`. 404 на удалении — файла уже
  нет (удалили в другой вкладке): для пользователя это тот же успех, строка
  просто уходит.
- **404 — это состояние страницы, а не ошибка загрузки.** Чужая и несуществующая
  встреча приезжают одинаковым 404 (api не подтверждает существование чужих
  записей), поэтому страница показывает «Встреча не найдена» с дорогой назад, а
  не алерт «попробуйте ещё раз», из которого нет выхода.
- **Встреча и файлы грузятся через `Promise.allSettled`, а не `all`.** Отказ по
  файлам не должен прятать уже пришедшую карточку встречи. Обратное неверно: при
  отказе по самой встрече блок файлов не рисуется вовсе — пустой список соврал
  бы, что файлов нет, а второй такой же алерт был бы тем же сообщением дважды.
- **Отказы 415, 413 и 409 показываются текстом api, а не своим.** Формат, размер
  и лимит файлов встречи api объясняет сам — по-русски и для показа как есть
  («Формат .zip не поддерживается»), поэтому `describeUploadFailure` берёт
  `message` из тела отказа (`apiMessageOf` в `utils/api.ts`). Обычно такой файл
  до api не доезжает, но рубеж там: разъехавшаяся копия лимитов или подмена типа
  приедут отсюда, и «попробуйте ещё раз» на них было бы тупиком. Остальные отказы
  api — английские служебные строки, вместо них остаются свои тексты.
- **401 обрабатывается тем же хелпером, что и в кабинете** (`handleUnauthorized`):
  тост «Сессия истекла», `logout()`, `/login` — или повтор, если кука уже с
  новым токеном. Сюда же попадает 401 на загрузке и удалении файла — токен мог
  истечь ровно между открытием страницы и выбором файла. Повторяется сам
  запрос (`sendFile`, `removeFile`), а не выбор файла и не вопрос «удалить?».
- **Зона — `UFileUpload` в варианте `area` без своего слота по умолчанию.** Со
  слотом `default` компонент не рендерит элемент зоны вовсе, а с ним и
  перетаскивание: так было в фазе 1, где в слоте стояла кнопка. Сама зона —
  `role="button"` с `tabindex="0"`: открывается кликом, Enter и пробелом, так
  что у перетаскивания есть одно-указательная и клавиатурная альтернатива
  (WCAG 2.2, «Dragging Movements»). Кнопку внутрь зоны не ставить: это
  вложенный интерактивный элемент внутри `role="button"`.

### Что проверено в браузере (страница встречи)

Прогон Playwright MCP, все цифры — замеры:

| Состояние                   | Что подтверждено                                                                |
| --------------------------- | ------------------------------------------------------------------------------- |
| пустой блок                 | текст-пояснение и кнопка загрузки, счётчик «0 файлов»                           |
| загрузка 5 МБ с кириллицей  | 201, имя «Отчёт за квартал.pdf» в списке, на диске `<id файла>.pdf` без `.part` |
| после перезагрузки          | файл на месте, размер «5 МБ», дата загрузки                                     |
| запись 1 ГБ (curl, chunked) | 201, RSS api 138.6 → 157.6 МБ (пик 170) — рост 19 МБ на гигабайтном файле       |
| чужая или несуществующая    | «Встреча не найдена», ссылка на список, ни одного алерта об ошибке              |
| негодный токен в куке       | тост «Сессия истекла», кука очищена, редирект на `/login`                       |
| api не запущен              | `role="alert"` «Нет связи с API» с «Повторить», блок файлов не рисуется         |
| api вернулся                | «Повторить» подтягивает и встречу, и файлы без перезагрузки                     |
| 360px и десктоп, обе темы   | `scrollWidth === clientWidth` (345/345), контраст текста 4.83–17.72:1           |
| ссылка со строки дашборда   | цель 147×32px, рамка фокуса 5.66:1, сдвиг вёрстки 0px                           |

Найденное этим прогоном:

- **Hover у solid-primary кнопки не проходит по контрасту: 3.01:1.** В покое
  белый на `--ui-primary` даёт 4.58:1, но `hover:bg-primary/75` осветляет фон до
  `#8987ff`, и текст на нём — 3.01:1 против нормы 4.5:1. Это дефолт темы Nuxt UI,
  а не наша разметка: он одинаково задевает «Войти» и «Создать аккаунт» на уже
  готовых страницах. Починено в фазе 7 в `app/app.config.ts` — см. «Дизайн-система».
- **Скрытый `input[type=file]` виден в дереве доступности как `button`.**
  `UFileUpload` рендерит его через `VisuallyHidden` с `aria-hidden="true"` и
  `tabindex="-1"`, но в снапшоте Playwright он всё равно появляется строкой
  `button [aria-hidden]`. Это не лишняя кнопка и не дефект — искать её причину
  второй раз не надо.
- **`browser_take_screenshot` без пути кладёт файл в корень репозитория,**
  а не в `.playwright-mcp/` — из `.gitignore` он там не прикрыт. Имя файла надо
  задавать с каталогом: `.playwright-mcp/<имя>.png`.
- **Файлы для загрузки должны лежать внутри репозитория.** MCP-сервер Playwright
  разрешает `browser_file_upload` только из своих корней (каталог проекта и
  `.playwright-mcp/`), на путь из системного temp отвечает «outside allowed
  roots».

Прогон фазы 2 (отказы api на загрузке), Playwright MCP, Chrome:

| Файл                     | Что подтверждено                                                           |
| ------------------------ | -------------------------------------------------------------------------- |
| `архив встречи.zip`      | 415, тост «Формат .zip не поддерживается», каталог встречи даже не создан  |
| документ 51 МиБ (`.pdf`) | 413 до чтения тела, тост «Документ больше 50 МБ», на диске ничего          |
| запись 2.1 ГиБ (`.mp4`)  | 413 за ~1 с, тост «Файл больше 2 ГБ» — после подъёма потолка Bun до 64 ГиБ |
| заметка `.txt` после них | 201, «1 файл», на диске ровно один `<id>.txt`                              |

Найденное этим прогоном:

- **Повторный выбор того же файла ничего не делает.** После отказа (или обрыва
  связи) пользователь выбирает тот же файл ещё раз — запроса нет, тоста нет.
  Причина в `UFileUpload`: нативный `input` он очищает в `watch(modelValue)`,
  когда модель становится пустой, а `onSelect` в `FilesSection.vue` сбрасывает
  `selected` в `null` в том же тике, что и получил файл. Watcher видит «было
  `null`, стало `null`», не срабатывает, `input.value` остаётся прежним — и
  браузер не шлёт `change` на тот же файл. Починено в фазе 5 штатным пропом
  `reset` у `UFileUpload` — он очищает `input` при каждом открытии диалога (см.
  «Неочевидности» выше); `nextTick` и `inputRef` не понадобились.
- **Запись больше потолка Bun рвёт соединение без ответа.** При прежнем потолке
  2 ГиБ + 64 МиБ запись на 2.1 ГиБ давала `net::ERR_CONNECTION_ABORTED` и тост
  «Нет связи с API»: Bun отвечает своим 413 без CORS-заголовков. Починено на api
  (замер 18 в ресерче); если «нет связи» снова появится только на больших
  файлах — первым делом смотреть `MAX_REQUEST_BODY_SIZE`.
- **Цикл загрузок через `waitForEvent('filechooser')` в
  `browser_run_code_unsafe` ломает сессию MCP.** Сервер сам перехватывает диалог
  выбора файла как «modal state», код его не получает, а очередь висящих
  диалогов растёт и блокирует остальные инструменты, вплоть до обрыва MCP на
  `browser_close`. Проверенный путь — клик по кнопке и `browser_file_upload`, по
  одному файлу за вызов.

Прогон фаз 5–7 (загрузка, просмотр, состояния и доступность), Playwright MCP,

Найденное этим прогоном:

- **CSS-переходы в окне браузера MCP не продвигаются.** `getComputedStyle` при
  hover возвращал стартовый цвет и через 400 мс: `transition-colors` стоит на
  месте, видимо, потому что окно в фоне. Замеры hover — только после
  `page.addStyleTag({ content: '* { transition: none !important }' })`, иначе
  «контраст при наведении» совпадает с контрастом в покое и врёт.
- **Под `page.route` у XHR-загрузки нет прогресса, а `route.fetch()` теряет тело
  файла.** Тело уходит перехватчику, `upload.onprogress` стоит на 0 %, а
  переотправленный запрос приехал на api пустым — в базу легли файлы по 0 байт.
  Подменять ответы загрузки через `page.route` нельзя; задержку ответа — тоже
  (фазу «Сохраняем…» так не увидеть). Подмена ответов отдачи и списка работает.
- **Фазу «Сохраняем…» в браузере увидеть не удалось.** На localhost между
  последним байтом и ответом 201 — миллисекунды, а оба способ растянуть окно
  ломают сам замер (см. выше; `latency` через CDP-сессию из отдельного вызова не
  пережила его конец). Логика простая — `upload.onload` → `phase: 'saving'`, —
  но живого подтверждения у неё нет.
- **Обрезок загрузки сохранился как готовый файл.** Отмена на ~31 % под
  эмуляцией сети оставила на диске 85 МБ из 200 со строкой в базе и ответом 201.
  Не воспроизвелось, но api теперь отбивает тело короче его `Content-Length`
  (замер 20 в ресерче). Если после отмены в списке появится файл — смотреть туда.
- **Имя полосы прогресса Reka задаёт сам.** Проп `aria-label` у `UProgress`
  перетирался `getValueLabel` по умолчанию — полоса называлась «0%», и процент
  читался дважды. Имя — через `:get-value-label`, значение словами — через
  `:get-value-text` с `plural` («31 процент», «34 процента»).
- **Скелетон карточки встречи был ниже карточки на 4px.** `h1` на десктопе —
  `sm:text-3xl` с высотой строки 36px, дата — `text-base`/24px, а заглушки — h-8 и
  h-5. Заголовок блока «Файлы» уезжал на 4px, когда приходили данные; после
  выравнивания высот — 0px на 360 и 1280.
- **Для точечных замеров `browser_snapshot` с `target`.** Полный снапшот страницы
  с 20 файлами — несколько тысяч строк, а `target: "main section"` и `depth`
  отдают ровно блок «Файлы».

## Документация

Полная таблица «что чем тянется» — в корневом `CLAUDE.md`, раздел «Документация
обновляется в том же коммите». Для фронтенда критичны два пункта:

- **Любая новая страница или правка `routeRules`** — обнови таблицу маршрутов в
  разделе «Главное: routeRules — это SEO-контракт» и раздел «Рендеринг во
  фронтенде» в `README.md`. Эта таблица не справочная: она единственное место, где написано,
  какие страницы индексируются, а какие сознательно отданы клиенту. Разошлась с
  `nuxt.config.ts` — и следующая правка SEO будет сделана по неверной картине.
- **Смена палитры, токенов или правил Nuxt UI** — раздел «Дизайн-система» здесь и
  пункт про Nuxt UI в «Тулинге» `README.md`. Сейчас там честно написано, что
  indigo/violet/zinc — заготовка; когда появится настоящий брендинг, эту оговорку
  надо снять.

Подключение UI-библиотеки, замена CSS-входа или переезд `srcDir` задевают ещё и
корневой `CLAUDE.md` (размещение зависимостей, `tailwindStylesheet` в
`.prettierrc.json`).
