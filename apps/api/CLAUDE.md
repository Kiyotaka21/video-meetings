## Стек

Elysia 1.4 на Bun, Prisma 7 к Postgres. Рантайм — именно Bun, не Node: `Bun.env`,
`bun --watch`, `bun build --target bun`, `Bun.password` для хеширования. Порт 3000.

```bash
bun run --filter @video-meetings/api dev        # или из корня: bun run dev:api
cd apps/api && bun run typecheck                # tsc --noEmit
cd apps/api && bun run test                     # bun test; из корня: bun run test
cd apps/api && bun run db:migrate                # prisma migrate dev
```

| `GET /health`                                                           | открытый                   |

## Загрузка файлов встречи: сначала ресерч, потом код

Фича описана тремя документами, и роли у них разные:

| Файл                                   | Отвечает за                                               |
| -------------------------------------- | --------------------------------------------------------- |
| `docs/prd-meeting-file-upload.md`      | что и зачем, без «как»                                    |
| `docs/plan-meeting-file-upload.md`     | порядок работ по фазам                                    |
| `docs/research-meeting-file-upload.md` | чем именно и обо что споткнёмся — замеры на наших версиях |

**Перед правкой `src/modules/files/*`, модели `MeetingFile` или роутов
`/meetings/:id/files` читай ресерч целиком, а не по диагонали.** Он не
справочник «на всякий случай»: в нём результаты запусков на Bun 1.3.14 и
Elysia 1.4.30 — и шесть мест, где рантайм ведёт себя не так, как читается из
документации, поэтому план приходится править. Например, забытый `await` у
`writer.write()` даёт +2423 МБ RSS на файле 1 ГБ вместо +6 МБ, а авто-`Range` у
`new Response(Bun.file(...))` через Elysia молча отвечает 200 вместо 206.

Замер в ресерче — записанный результат запуска, а не цитата из документации.
Разошёлся с поведением — значит поехала версия: чинить надо версию или замер, а
не обходить его на месте. Найденное сверх ресерча дописывается туда же, в раздел
«Проверено замером», иначе следующий агент потратит на поиск тот же час.

## Зачем entry разбит на три файла

```
src/index.ts        только listen — точка входа
src/app.ts          сборка плагинов, экспортирует app и тип App
src/modules/        доменные модули = плагины Elysia
src/config/env.ts   всё чтение окружения
```

Разделение `index.ts` / `app.ts` не косметическое:

- `app.ts` не открывает порт, поэтому его можно импортировать в тестах и дёргать
  через `app.handle(new Request(...))` без поднятия сервера;
- `app.ts` экспортирует `export type App = typeof app` — это то, что нужно
  Eden Treaty, чтобы дать фронтенду типизированный клиент. Тип обязан отражать
  всю цепочку `.use(...)`, поэтому новые модули подключай в `app.ts`, а не
  навешивай на инстанс где-то ещё.

Новый домен — это новый файл в `src/modules/`, экспортирующий инстанс Elysia с
`prefix` и `tags`, и одна строка `.use(...)` в `app.ts`. Домен, которому тесно в
одном файле, становится каталогом: роуты в `index.ts`, остальное рядом
(`src/modules/files/` — образец), а импорт в `app.ts` не меняется.

## Данные: Prisma 7

```
prisma/schema.prisma       модели
prisma/migrations/         история миграций, коммитится
prisma.config.ts           конфиг CLI: путь к схеме и DATABASE_URL
generated/prisma/          сгенерированный клиент, в git не попадает
src/db/prisma.ts           единственный инстанс PrismaClient
```

Четыре вещи, которые отличают семёрку от привычной Prisma и ломают код, если про
них не знать:

- **Клиент не работает без драйверного адаптера.** Rust-движка в 7 нет, запросы
  исполняет query compiler поверх драйвера, поэтому `new PrismaClient()` без
  `adapter` не заведётся. Здесь стоит `@prisma/adapter-pg` (тянет `pg` сам).
- **`DATABASE_URL` задаётся в `prisma.config.ts`, а не в блоке `datasource`.** В
  схеме остался только `provider`; строка подключения приходит из конфига через
  `env('DATABASE_URL')`.
- **CLI зовётся как `bunx --bun prisma`, и это не косметика.** `env()` из
  `prisma/config` рассчитывает, что `.env` подгрузил рантайм. Bun это делает,
  Node — нет, так что под `npx prisma` (или `bunx` без `--bun`) `DATABASE_URL`
  окажется пустым, а команда — «непонятно почему» неработающей. Все скрипты в
  `package.json` уже с `--bun`; альтернатива — тащить `dotenv` ради одного импорта.
- **Импорт клиента — из `../../generated/prisma/client`, а не из `@prisma/client`.**
  Генератор `prisma-client` кладёт исходники в `generated/`, каталог в
  `.gitignore`, `.prettierignore` и в ignores ESLint. После клона и после правки
  схемы его надо пересобрать: `bun run db:generate` (и то же самое делает
  `postinstall`, так что обычный `bun install` закрывает вопрос).

В базе имена в snake_case (`password_hash`, `users`), в коде — camelCase; связывает
их `@map`/`@@map` в схеме. Правка схемы без миграции в том же коммите — способ
получить рассинхрон, который вылезет у следующего разработчика на `db:migrate`.

## Аутентификация

`src/modules/auth.ts`: открытые регистрация и вход, закрытые `/auth/me` и guard
для остальных модулей. Что здесь сделано намеренно и не должно «упроститься» при
следующей правке:

- **Пароли хеширует `Bun.password`** (argon2id по умолчанию) — внешняя библиотека
  не нужна. В базе лежит только хеш, наружу не отдаётся даже он: ответ
  регистрации, входа и смены пароля — `{ token }` и ничего больше.
- **Границы пароля (8–128) — одна схема `password`** на регистрацию, вход и оба
  поля смены пароля, а не копии чисел. Разъехавшись, они дали бы пароль, который
  можно поставить, но нельзя ввести при входе. Копия на клиенте —
  `apps/web/app/utils/auth.ts`.
- **Занятость e-mail ловится по ошибке `P2002`, а не проверкой `findUnique` перед
  вставкой.** Между такой проверкой и `create` есть окно, в которое пролезает
  второй запрос; unique-индекс закрывает его сам, а обработчик просто переводит
  P2002 в 409.
- **Логин отвечает одинаково на неизвестный e-mail и на неверный пароль** — один и
  тот же 401 с одним и тем же телом. Иначе ответ становится оракулом, по которому
  перебирают зарегистрированные адреса.
- **Пароль сверяется даже когда пользователь не найден**, с константой
  `ABSENT_USER_PASSWORD_HASH`. Без этого argon2 отрабатывает только в одной из
  веток, и тот же перебор идёт по времени ответа.
- **E-mail нормализуется в нижний регистр** перед записью и перед поиском, иначе
  `Foo@` и `foo@` заводят две учётки.

### `GET /auth/me`

Отдаёт `{ id, email, name }` текущего пользователя — фронтенду нужны адрес и
имя вошедшего, чтобы показать их в кабинете. `name` в ответе есть всегда: `null`
значит «не задано», и клиенту не нужно отличать его от пропавшего ключа. Два
решения здесь неочевидны:

- **Маршруты `/auth/me` вынесены в отдельный инстанс `currentUserRoutes`, а не
  дописаны к `authModule` после `.use(authenticated)`.** Hook'и Elysia действуют
  на роуты, объявленные после них: при дописывании порядок строк в файле начал бы
  решать, открыт `/auth/register` или закрыт. Отдельный инстанс делает границу
  видимой — под guard'ом ровно то, что внутри него. Что register и login остались
  открытыми, проверяют их собственные тесты: они ходят без токена.
- **Годная подпись при отсутствующем пользователе — это 401, а не 404.** Учётку
  удалили или токен выпущен против другой базы; для клиента это ровно та же
  мёртвая сессия, что и истёкший `exp`. Один код на все случаи позволяет
  фронтенду держать одну ветку «401 → выйти и на /login» вместо разбора 404,
  который иначе выглядел бы как «такой страницы нет».

Адрес берётся из базы, а не из `email` в payload'е токена: иначе `/auth/me`
подтверждал бы сам токен, а не состояние пользователя, и переименование адреса
в базе не доезжало бы до клиента до перевыпуска токена.

### `PATCH /auth/me` — имя

Тело `{ name }`, ответ — тот же объект, что у `GET /auth/me` (поля задаёт один
`publicUser`): фронтенд кладёт его в общий `user` без повторного запроса.
Пробелы по краям срезаются, пустое после обрезки — сброс в `null`; пустой
строки в колонке не бывает. Неочевидное:

- **Граница «до 50 после обрезки» зашита в `pattern` схемы, а не проверяется в
  обработчике.** Схема видит сырую строку, и `maxLength: 50` отбил бы честное
  `"  " + 50 символов + "  "`. Шаблон описывает строку целиком — пробелы, до 50
  символов от видимого до видимого, пробелы, — и отказ остаётся обычным 422
  валидатора, а не второй веткой со своим телом ответа.
- **Хвостовые пробелы стоят в шаблоне внутри необязательной группы.** Форма
  `^\s*(…)?\s*$` квадратична на строке из пробелов перед чужим символом: 40 000
  пробелов и перевод строки — 2 с на один запрос, а тело JSON api читает любого
  размера. Текущая форма — 0 мс там же и около 30 мс на мегабайт вместе с
  разбором JSON. «Упростишь» шаблон — проверь замером, тесты этого не ловят.
- **Управляющие символы — 422 где угодно, даже по краям**, хотя `trim()` срезал
  бы перевод строки молча. Управляющие — категория Cc (`U+0000–U+001F`,
  `U+007F–U+009F`) плюс разделители строк и абзацев `U+2028`, `U+2029`;
  срезаемые пробелы — то, что срезает `trim()`, за вычетом их же (Zs и BOM).
  Поэтому после проверки шаблоном `trim()` трогает только пробелы.
- **Длина — в UTF-16 code units**, как `maxLength` у `credentials` и
  `String.length` в браузере: эмодзи считается за два. Копия правил на клиенте
  (`validateName` в `apps/web/app/utils/profile.ts`) обязана считать так же.
- **Удалённый пользователь с живым токеном — 401.** `update` по несуществующей
  строке бросает P2025, обработчик переводит его в ту же мёртвую сессию, что и
  на `GET`.

### `POST /auth/me/password` — смена пароля

Тело `{ currentPassword, newPassword }`, ответ — `{ token }` новой версии. Смена
поднимает `tokenVersion`, и все токены, выпущенные раньше, — с любого устройства
и в том числе тот, с которым пришёл запрос, — получают 401 (как устроена
сверка — в «Guard для закрытых маршрутов»). Неочевидное:

- **Неверный текущий пароль — 403, а не 401.** На фронтенде 401 от api — это
  «сессия кончилась» (`isUnauthorized`): страница гасит куку и уводит на
  `/login`. Отвечай смена пароля 401-м, опечатка в поле формы выкидывала бы
  пользователя из системы. Пароль после 403 прежний, сессии живы.
- **Новый, равный текущему, — 400, и проверяется после текущего.** Иначе на
  неверный текущий, совпавший с новым, ответ «совпадает с текущим» был бы
  неправдой. Сравниваются поля тела, второй argon2 не нужен: текущий уже
  сверен с хешем.
- **Тексты 403 и 400 — по-русски, для показа как есть** («Текущий пароль
  неверен», «Новый пароль совпадает с текущим»), как 415/413/409 у файлов: оба
  про конкретное поле формы.
- **Текущий пароль подчиняется тем же 8–128, что и новый,** — 422 вне них, как и
  на входе: такого пароля нет ни у кого, а `maxLength` не даёт гонять argon2 по
  мегабайтной строке.
- **Хеш и версия меняются одним `update`** (`tokenVersion: { increment: 1 }`):
  нет момента, когда пароль уже новый, а старые токены ещё проходят. Новый токен
  в ответе подписан версией, которую вернул этот же `update`, — без него
  вкладка, сменившая пароль, вышла бы из системы вместе со всеми.

### Guard для закрытых маршрутов

`src/modules/auth.ts` экспортирует не только роуты, но и плагин `authenticated`.
Закрыть новый модуль — это одна строка `.use(authenticated)`, после неё в
контексте появляется `userId`, а запрос без годного токена до обработчика не
доходит. Смотри `src/modules/meetings.ts` как образец.

- **`as: 'scoped'` у `resolve` обязателен.** Без него проверка и `userId`
  останутся внутри самого плагина, подключивший модуль их не увидит — и роут
  тихо станет открытым, а не сломается заметно.
- **Плагин `jwt` создаётся один раз** (`jwtPlugin`) и подключается и в выдачу
  токенов, и в guard. Elysia дедуплицирует плагины по имени, так что секрет и
  срок жизни не разъедутся между `sign` и `verify`.
- **`jwt.verify` возвращает `false` на любую негодность разом** — чужая подпись,
  битый формат, истёкший `exp`. Отдельно их не разбираем: клиенту во всех случаях
  один и тот же 401.
- **Токен без `sub` — тоже 401.** Подпись у него наша, но пользователя по нему не
  найти, и без явной проверки `userId` уехал бы в запрос как `undefined`.
- **Guard ходит в базу на каждом закрытом запросе.** Подпись и `exp` говорят
  только, что токен выпустили мы, а не что сессия жива: пароль могли сменить,
  учётку — удалить. После `verify` guard читает `tokenVersion` по первичному
  ключу — одну колонку — и сверяет с claim `ver`; расхождение или пропавшая
  строка — тот же 401. Цена — индексный SELECT на запрос. До этого удалённый
  пользователь с живым токеном получал на `GET /meetings` 200 с пустым списком, а
  на `POST /meetings` — пятисотку на внешнем ключе.
- **Отзыв сессий — счётчик, а не сравнение `iat` со временем смены пароля.**
  `iat` точен до секунды: токен, выпущенный за мгновение до смены, и новый,
  выданный в ответ на неё, по времени неразличимы — либо выживет старый, либо
  умрёт новый. У счётчика такого края нет: смена пароля делает
  `tokenVersion: { increment: 1 }`, и все токены с прежним `ver` мертвы, сколько
  бы ни прошло времени.
- **Токен без `ver` — версия 0.** Так выглядят токены, выпущенные до появления
  счётчика, а 0 — `@default` колонки: выкатка никого не разлогинивает, а первая
  же смена пароля отзывает и их. Сравнение строгое — `ver` выпускается только
  числом, и `"0"` получает 401, а не проходит за ноль.
- **Claims собирает одна функция `sessionClaims`** — у регистрации, входа и
  смены пароля. Маршрут, который забыл бы `ver`, выдавал бы токены «версии 0»:
  у пользователя, уже менявшего пароль, они умирали бы сразу после выдачи.

### Встречи

`src/modules/meetings.ts`. Неочевидное:

- **Владелец подставляется в `where`, а не проверяется после выборки.** Чужая
  встреча не находится вовсе, и `GET /meetings/:id` отвечает на неё тем же 404,
  что и на несуществующий id. 403 подтвердил бы, что такая встреча есть.
- **`participants` — массив адресов, а не связь с `users`.** Приглашать можно и
  тех, кто ещё не зарегистрирован. Адреса приводятся к нижнему регистру и
  дедуплицируются — тем же правилом, что и e-mail в `users`.
- **Даты наружу уходят строго `toISOString()`.** На вход принимается любой
  корректный ISO-8601 (в том числе со смещением `+03:00`), в ответе — всегда UTC
  с миллисекундами; клиенту не приходится гадать, в каком виде вернётся дата.
- **Список отсортирован по `date` по возрастанию** — ближайшие первыми; под это
  заведён составной индекс `(owner_id, date)`.
- **Удаления встречи нет, и когда оно появится, оно обязано убрать файлы с
  диска.** Каскад `onDelete: Cascade` удаляет строки `meeting_files`, но не сами
  файлы: `DELETE /meetings/:id` после удаления строки зовёт
  `removeMeetingFiles(meetingId)` из `src/modules/files/storage.ts`, иначе
  каталог встречи останется в `UPLOAD_DIR` навсегда. Функция уже есть и покрыта
  тестом (`tests/file-delete.e2e.test.ts`), напоминание стоит и в шапке
  `meetings.ts`.

### Файлы встречи

`src/modules/files/` — каталог, а не файл. Перед правкой — ресерч, см. раздел
выше.

| Файл         | Что в нём                                                                              |
| ------------ | -------------------------------------------------------------------------------------- |
| `index.ts`   | маршруты владельца под `authenticated`: приём, список, удаление                        |
| `content.ts` | отдача по ссылке: свой инстанс без guard'а, `Range`, `Content-Disposition`             |
| `link.ts`    | файловый токен: плагин `fileJwt` на производном секрете, путь отдачи                   |
| `limits.ts`  | форматы, размер по группе, 20 файлов на встречу — их читают и тесты                    |
| `storage.ts` | диск: запись тела в `.part`, пути внутри `UPLOAD_DIR`, уборка файла и каталога встречи |

- **Тело запроса не парсится (`parse: 'none'`) и уходит на диск потоком.**
  `request.formData()` в Bun собирает файл в память целиком, а лимит на запись —
  2 ГБ. С `parse: 'none'` `request.body` остаётся нетронутым `ReadableStream`,
  который обработчик сливает в `Bun.file(...).writer()` сам.
- **`await` у каждой `writer.write()` — это и есть «потоком, а не в память».**
  `write()` возвращает промис, когда запись отложена; без ожидания цикл читает
  сокет быстрее, чем пишет диск, и буфер растёт до размера файла. Замер на 1 ГБ:
  +6 МБ RSS с `await` против +2423 МБ без него. Ни типы, ни тесты на мелких
  файлах этого не ловят — отсюда комментарий прямо у строки.
- **Имя и тип приходят заголовками, и имя обязано быть percent-encoded.**
  Значение HTTP-заголовка — байты Latin-1: `new Headers({ 'x-file-name':
'Отчёт.pdf' })` бросает исключение и в браузере, и в Bun. Контракт —
  `encodeURIComponent` на клиенте, `decodeURIComponent` здесь; битая строка
  (`%zz`) — это 400, а не 500.
- **Путь на диске генерирует сервер целиком** — `<UPLOAD_DIR>/<id встречи>/<id
файла><расширение>`, где расширение — ключ таблицы форматов, а не хвост имени.
  Исходное имя живёт только в метаданных, поэтому `../` в имени никуда не уводит.
- **Формат решает расширение, заявленный тип только подтверждает.** Расширения
  нет в `FORMATS` — 415; тип пустой или `application/octet-stream` —
  пропускаем; тип непустой и не из `accepts` своего расширения — 415. Буквальное
  «расширение или тип вне списков» отбило бы честный `.m4a` из Chrome на
  Windows: тип браузер берёт из реестра ОС, и для `.m4a`, `.webm` он там часто
  пуст, а `.csv` при установленном Excel приезжает как `application/vnd.ms-excel`.
  Отказ по формату — до `mkdir`: он не стоит ни каталога, ни байта тела.
- **В `mimeType` пишется канонический тип формата, а не заявленный.** Иначе
  `.pdf`, загруженный с `Content-Type: text/html`, при отдаче уехал бы HTML'ем с
  origin'а api — хранимая XSS. Поэтому `mimeType` в метаданных — функция
  расширения, и отдача берёт `Content-Type` прямо оттуда (плюс `nosniff`).
- **413 проверяется дважды: по `Content-Length` до чтения тела и счётчиком в
  потоке.** Заголовок — основной рубеж: браузер шлёт его у файла всегда, и только
  отказ до чтения тела гарантированно доезжает до клиента. Счётчик ловит клиента,
  который соврал или не прислал заголовок (chunked): на превышении цикл
  обрывается, лишний чанк на диск не уходит, `.part` удаляется. Лимит берётся от
  группы формата, поэтому 415 стоит раньше 413 — без формата не знаешь лимита.
- **Тело короче своего `Content-Length` — 400, файл не сохраняется.** Обычно обрыв
  приходит `AbortError` из цикла чтения, но прогон в браузере один раз оставил
  обрезок 85 МБ из 200 как готовый файл: поток закончился без ошибки, а механизм
  так и не воспроизвёлся (ресерч, замер 20). Сверка записанных байт с заголовком
  закрывает это при любом механизме; тело без заголовка (chunked) сверять не с
  чем. Поэтому тестам нельзя заявлять `declaredSize` больше тела — нужны
  настоящие байты (`zeros()`).
- **409 на лишний файл решает счёт под замком на строке встречи.** Счёт до записи
  — только дешёвая отсечка, чтобы лишний файл на 2 ГБ не ложился на диск ради
  отказа. Окончательно решает транзакция при вставке: `SELECT ... FOR UPDATE` на
  встречу, счёт, вставка. Одной транзакции мало — в Postgres по умолчанию
  READ COMMITTED, и `count` в ней ничего не блокирует: два параллельных запроса
  оба насчитают 19 и оба вставят двадцатый. Отказ при вставке удаляет `.part`.
- **Тексты 415, 413 и 409 — по-русски и рассчитаны на показ пользователю как
  есть** («Формат .zip не поддерживается», «Файл больше 2 ГБ», «Достигнут лимит:
  …»), в отличие от английских служебных сообщений остальных ответов, вместо
  которых фронтенд подставляет свой текст.
- **Файл публикуется переименованием `.part` после вставки строки в базу.** Пока
  он пишется, его имени нет ни в одной строке, и читатель недописанного не
  увидит; уборка после любого отказа — удаление одного `.part`. Обрыв соединения
  клиентом виден как `AbortError` из цикла чтения, отдельно слушать
  `request.signal` не нужно.
- **Размер хранится `BigInt`, а наружу уходит `Number`.** Максимум `Int` в
  Postgres — 2 147 483 647 байт, файл ровно на 2 ГиБ туда не влезает; но `BigInt`
  в ответе роняет сериализацию пятисоткой «JSON.stringify cannot serialize
  BigInt». Конвертация — на границе ответа, рядом с `toISOString()`.
- **Список сортируется по `(createdAt, id)`, а не по одному `createdAt`.**
  Точность колонки — миллисекунда, и две загрузки подряд в неё укладываются;
  вторым ключом идёт `id` (uuid v7, то есть тоже по времени), иначе порядок
  одинаковых меток не определён и тест на него мигает.

#### Удаление файла

- **Сначала строка, потом диск.** Файл без строки безвреден — он уйдёт вместе с
  каталогом встречи, — а строка без файла даёт битую ссылку в интерфейсе.
  Ссылка, выданная до удаления, сразу отвечает 404: отдача ищет строку раньше,
  чем читает диск, а её уже нет.
- **Удаление — один `delete` по паре (файл, встреча), без `findFirst` перед
  ним.** Prisma 7 принимает неуникальные поля в `where` у `delete`; не нашлось —
  P2025, который обработчик переводит в 404. Из двух одновременных удалений
  второе получает 404, а не 500 — между выборкой и удалением не было бы окна.
- **Читающего файл удаление не ломает.** На Windows `rm` проходит, пока файл
  отдаётся по ссылке, и читатель дочитывает до конца (ресерч, замер 11), так что
  очереди отложенного удаления не нужно.
- **`removeMeetingFiles` отказывается от пустого id и `..`.** Каталог считается
  через `meetingDirectory`, которая проверяет, что путь внутри `UPLOAD_DIR` и не
  равен ему: иначе кривой аргумент стал бы `rm -rf UPLOAD_DIR`.

#### Отдача файла по ссылке

`<video src>` и `<a href>` не умеют слать `Authorization`, поэтому у каждого
файла в ответах `GET` и `POST /meetings/:id/files` есть поле `url` — путь отдачи
с коротким файловым токеном в `?token=`.

- **Файловый токен подписан секретом, выведенным из `JWT_SECRET`** (HMAC с
  меткой `file-link-v1`), а не самим `JWT_SECRET`, как предлагал план. На общем
  секрете guard `authenticated` принял бы файловый токен за сессию: `GET
/meetings` ответил бы 200 с пустым списком, `POST /meetings` — пятисоткой
  (ресерч, 2.3). Claim вроде `typ: 'file'` закрыл бы только одну сторону и только
  пока о нём помнят; разные секреты делают путаницу невозможной. `sub` — id
  файла, срок — `FILE_LINK_EXPIRES_IN` (15 минут). Тесты выводят секрет сами,
  поэтому подмена на `JWT_SECRET` их роняет.
- **Плагин — второй инстанс `jwt` со своим именем `fileJwt`.** Elysia
  дедуплицирует плагины по имени: с именем `jwt` он слился бы с сессионным.
- **`url` — путь от корня api, а не абсолютный адрес.** Api не знает, под каким
  origin'ом его видит браузер (прокси, другой порт); фронтенд склеивает путь со
  своим `apiUrl`, как `$fetch` — с `baseURL`.
- **Отдача — свой инстанс `fileContentRoutes` без guard'а.** Как и
  `currentUserRoutes` в `auth.ts`: граница видна глазами, под guard'ом ровно то,
  что внутри инстанса. Модуль собирает оба: `new Elysia().use(ownerRoutes)
.use(fileContentRoutes)`.
- **401 и 404 разведены по смыслу.** Нет токена, чужая подпись (в том числе
  сессионный токен), истёкший `exp`, токен соседнего файла — 401: ссылка не даёт
  доступа. Годный токен, но файла нет в этой встрече (чужой id в пути, удалённая
  строка, файл пропал с диска) — 404.
- **Перед чтением — проверка строки в базе и `exists()` на диске.** `Bun.file`
  на несуществующий путь даёт размер 0 и пустое тело без ошибки (замер 10): без
  проверки рассинхрон «строка есть, файла нет» отвечал бы «успешным» пустым 200.
  Один stat на запрос, а не на чанк — чанки идут внутри ответа.
- **`Range` написан руками, и кусок отдаётся через `.slice(...).stream()`.**
  Авто-`Range` Bun через Elysia не работает (замер 4, elysia#1868), а у ручного
  есть своя ловушка — см. «Ловушки». `Content-Length` ставится явно: без него
  ответ уходит chunked, и `<video>` не знает длительности. `Accept-Ranges: bytes`
  — во всех ответах, по нему плеер решает, показывать ли перемотку; брак и
  несколько диапазонов — весь файл с 200, начало за концом файла — 416 с
  `Content-Range: bytes */<размер>`.
- **`Content-Disposition: attachment` всегда, в двух формах.** К подресурсам
  (`<video>`) браузер его не применяет, так что один заголовок закрывает и плеер,
  и скачивание. `filename*=UTF-8''…` по RFC 5987 несёт кириллицу и пробелы
  (`'()*` кодируются сверх `encodeURIComponent`), `filename="…"` — печатный ASCII
  для старых клиентов: сырую кириллицу не пропустит даже конструктор `Headers`.

## Тесты

Раннер — встроенный `bun test`, без Vitest и без Jest.

```
tests/setup.ts          preload: фиксирует окружение до импорта приложения
tests/helpers/http.ts   обёртка над app.handle, сырой ответ для отдачи файла
tests/helpers/jwt.ts    разбор и выпуск JWT без зависимостей
tests/helpers/files.ts  встреча, контракт полей файла, что лежит на диске
tests/*.e2e.test.ts     контракты маршрутов
```

E2E здесь — это `app.handle(new Request(...))`, а не запросы на порт. Через
`handle` проходит весь конвейер (CORS, валидация схем, обработка ошибок,
сериализация), но сервер не поднимается: тесты не дерутся за порт 3000 с
запущенным `bun run dev`.

Через `prisma` напрямую тест ходит в одном случае — когда изображает соседний
запрос в гонке (см. «Ловушки»): `app.handle` не даёт управлять тем, в какой
момент запрос дойдёт до вставки.

Три вещи, которые важно не сломать:

- **`tests/setup.ts` подключён как `preload` в `bunfig.toml`, и порядок тут
  критичен.** `src/config/env.ts` читает `Bun.env` один раз, на загрузке модуля;
  если выставлять переменные внутри теста, приложение успеет импортироваться со
  старыми значениями. Всё, что тесту нужно от окружения, задаётся в `setup.ts`.
- **Тесты ходят в настоящую базу** (`bun run db:up` плюс накатанная схема,
  `bun run db:migrate`), моков нет — иначе «регистрация создаёт пользователя,
  логин ищет существующего» не проверить. Данные между прогонами не чистятся,
  поэтому e-mail'ы генерируются уникальными (`e2e-${randomUUID()}@example.com`);
  фикстуры с постоянными адресами упадут на втором запуске.
- **JWT в тестах разбирается вручную** (`tests/helpers/jwt.ts`, `node:crypto`), а
  не библиотекой, которой он выпущен. Иначе тест проверял бы сам себя: контракт
  здесь — формат RFC 7519 и подпись HS256 секретом из `JWT_SECRET`, а не выбор
  библиотеки.

`bun run check` тесты не запускает — гейт не должен требовать Docker.

## Ловушки, на которые уже наступали

**`.get('', ...)`, а не `.get('/', ...)` при заданном `prefix`.** Оба варианта
отвечают на `/health`, но со слэшем в OpenAPI-спеку попадает путь `/health/` — с
лишним хвостом. Смотри `src/modules/health.ts` как образец.

**Плагин `@elysiajs/swagger` мёртв** — застыл на 1.3.1 и не поддерживает Elysia 1.4.
Актуальная замена, которая здесь и стоит, — `@elysiajs/openapi`.

**Порядок плагинов значим.** `cors` подключается первым, до роутов, иначе часть
ответов уедет без CORS-заголовков.

**`toMatchObject` в `bun test` подменяет совпавшие поля матчером прямо в
проверяемом объекте.** После
`expect(body).toMatchObject({ token: expect.any(String) })` в `body.token` лежит
не строка, а `Any<String>`, и следующая же строка теста падает с
`token.split is not a function`. Поэтому в `tests/` асимметричных матчеров нет:
тип проверяется через `expect(typeof value).toBe('string')`.

**Гонку не поймать «N запросами через `Promise.all`».** Тест «пять (и десять)
параллельных загрузок на последнее место» проходил и **без** `FOR UPDATE`:
транзакции Prisma идут параллельно (замер: три стартуют за 12 мс), но через
`app.handle` запросы доходят до вставки вразнобой, и окно между счётом и вставкой
не перекрывается. Такой тест зелёный при любом коде, то есть не проверяет ничего.
Рабочий приём — разыграть соседа самому: тест держит открытую транзакцию с
замком и уже вставленной строкой, ждёт по `pg_stat_activity`
(`wait_event_type = 'Lock'`), пока запрос встанет в очередь, и только тогда
коммитит. Образец — тест на 409 в `tests/files.e2e.test.ts`; без замка в
обработчике он краснеет три прогона из трёх. Ждать опросом, а не `sleep`: на
медленной машине фиксированной паузы не хватит, и тест молча перестанет
проверять гонку.

**Кусок файла теряет конец, если Elysia переупаковала ответ.** `new
Response(Bun.file(p).slice(0, 100))` сам по себе отдаёт 100 байт, но
`new Response(thatResponse.body)` — уже файл до конца: поток `body` у такого
ответа конец куска не держит. Elysia переупаковывает ответ именно так, как
только в `set.headers` что-то есть, — а там всегда CORS. Итог: на `bytes=0-99`
уходило 206 с `Content-Range: bytes 0-99/1000` и тысячей байт тела, причём
только у диапазонов, которые кончаются не на конце файла. Лечится
`slice(...).stream()` — поток из него конец держит (замер 19 в ресерче). Ресерч
мерил ручной `Range` на маршруте без `set.headers` и этого не увидел.

**`$queryRaw` не переваривает колонку типа `void`.** `SELECT pg_sleep(0.2)`
через `$queryRaw` падает с P2010 `UnsupportedNativeDataType` — адаптер не знает,
во что превратить `void`. Для запросов без результата — `$executeRaw`, либо
привести колонку: `pg_sleep(0.2)::text`.

## Схемы ответов кормят документацию

`@elysiajs/openapi` строит спеку из typebox-схем, а не из типов TypeScript. Роут без
`response`-схемы попадёт в `/docs` пустой заглушкой. Поэтому у новых роутов задавай
`response` через `t` и короткий `detail.summary`:

```ts
.get('', handler, {
  detail: { summary: 'Liveness probe' },
  response: t.Object({ status: t.Literal('ok') }),
})
```

Scalar UI — на `/docs`, сырая спека — на `/docs/json`. В production и то и другое
отключено через `enabled: !isProduction`.

Маршрут под `authenticated` дополнительно помечается `detail.security`
(`[{ bearerAuth: [] }]`) — сама схема `bearerAuth` объявлена в `app.ts`. Без этой
пометки в Scalar не будет поля для токена, и роут будет выглядеть открытым. Код
401 стоит держать в `response`-карте таких роутов: это и документация, и разрешение
Elysia отдать такой ответ из guard'а.

## Окружение

Читается только в `src/config/env.ts`, через `Bun.env`, и раздаётся дальше как
готовый объект `env`. Не тяни `Bun.env` напрямую в модули.

`CORS_ORIGINS` — список origin'ов через запятую, парсится там же. Новый разрешённый
адрес добавляется переменной окружения, не хардкодом в `app.ts`. Дефолт —
`http://localhost:5173`, то есть dev-сервер Nuxt; он должен совпадать с
`devServer.port` во фронтенде.

| Переменная              | Дефолт                  | Кто читает                                           |
| ----------------------- | ----------------------- | ---------------------------------------------------- |
| `PORT`, `HOST`          | `3000`, `0.0.0.0`       | `src/index.ts`                                       |
| `CORS_ORIGINS`          | `http://localhost:5173` | `app.ts` через `env.corsOrigins`                     |
| `DATABASE_URL`          | нет                     | `src/db/prisma.ts` и Prisma CLI                      |
| `JWT_SECRET`            | нет                     | `src/modules/auth.ts`                                |
| `JWT_EXPIRES_IN`        | `7d`                    | там же, формат jose: `15m`, `7d`                     |
| `FILE_LINK_EXPIRES_IN`  | `15m`                   | `src/modules/files/link.ts`, срок ссылки на файл     |
| `UPLOAD_DIR`            | `./.uploads`            | `src/modules/files/storage.ts` через `env.uploadDir` |
| `MAX_REQUEST_BODY_SIZE` | 64 ГиБ                  | `src/index.ts` → `app.listen`                        |

**У `DATABASE_URL` и `JWT_SECRET` дефолта нет намеренно.** `env.ts` бросает
исключение на старте, если их не задали. Дефолт у секрета подписи — это дыра,
которая тихо доезжает до production и там выглядит как рабочая конфигурация;
падение при старте заметно сразу.

**А у `UPLOAD_DIR` дефолт есть, и это не непоследовательность.** Отсутствие
каталога загрузок дыры не создаёт, в отличие от предсказуемого секрета подписи, а
падение api при старте на свежем клоне — лишнее трение. Относительный путь
`env.ts` разворачивает в абсолютный сразу: рабочий каталог у `bun run dev:api` и
у `bun test` разный, и относительный уехал бы следом за ним.

**`MAX_REQUEST_BODY_SIZE` — это потолок Bun.serve, а не наш лимит, и держится он
далеко за любым правдоподобным файлом (64 ГиБ), а не «чуть выше 2 ГиБ».** Запрос
с `Content-Length` сверх потолка Bun отбивает сам, до обработчика: его
`413 Request Entity Too Large` уходит без CORS-заголовков, а соединение рвётся
посреди отправки — в браузере это `net::ERR_CONNECTION_ABORTED` и «нет связи», а
не «Файл больше 2 ГБ». Ровно так было при прежнем потолке 2 ГиБ + 64 МиБ с
записью на 2.1 ГиБ — в 64 МиБ зазора попадали бы только файлы от 2 до 2.06 ГиБ.
Наш 413 по заявленному размеру срабатывает раньше, если запрос до него доходит,
поэтому потолок должен пропускать к обработчику всё, что может прислать живой
пользователь. От раздутого JSON на остальных роутах потолок не защищает ни при
2 ГиБ, ни при 64: Elysia читает такое тело в память целиком, и это отдельная
задача. Через `app.handle` настройка не действует вовсе — тесты её не покрывают,
проверять только на запущенном сервере (замер 18 в ресерче).

В тестах `JWT_SECRET` подменяется в `tests/setup.ts`, чтобы прогон не зависел от
локального `.env`; `DATABASE_URL` берётся из `.env` как есть — тестам нужна
настоящая база. `UPLOAD_DIR` там же переводится на временный каталог, который
убирается после прогона: писать загрузки в рабочий каталог тесты не должны.

## Документация

Полная таблица «что чем тянется» — в корневом `CLAUDE.md`, раздел «Документация
обновляется в том же коммите». Для бэкенда чаще всего срабатывает такое:

- **новый модуль в `src/modules/`** — если он вводит неочевидное правило, опиши его
  здесь; рутинный CRUD-модуль документировать не нужно, он читается из кода;
- **новый плагин Elysia** — сюда и в раздел «Тулинг» в `README.md`, с указанием,
  почему выбран именно он (как это сделано для `@elysiajs/openapi` против мёртвого
  `@elysiajs/swagger`);
- **новая переменная окружения** — `.env.example` и таблица в разделе «Окружение»;
- **правка `prisma/schema.prisma`** — миграция в том же коммите; новая таблица —
  ещё и раздел «База данных» в `README.md`;
- **смена порта или CORS-политики** — ещё и корневой `CLAUDE.md`, там описана
  связка порта фронтенда с `CORS_ORIGINS`;
- **новая ловушка**, на поиск которой ушло время — в «Ловушки, на которые уже
  наступали», обязательно с причиной, а не только с рецептом.
